見た目以上に重要な失敗モードが 2 つあります。どちらの場合もパイプラインが
動いているように見えるからです。

* **委譲したエージェントが応答しなくなり**、誰も気づかない。ブロックした
  呼び出しは遅い呼び出しと見分けがつかないためです。
* **ループが終わらない** — レビュー、修正、再レビュー、あるいはもっと目立たない
  修正→テスト→修正 — 収束しないままトークンを消費し続けます。

以下のすべては、この 2 つのために存在します。指針となるルールは、*助言する*
だけのガードはガードではない、ということです。ここでの制限はどれも、それを
超えようとするアクション自身によって強制されます。最初のバージョンは
レビュー予算を照会コマンドで表示するだけで、どこでも強制しておらず、
そのため何も止められなかったからです。

<a id="stalls"></a>

## stall

<a id="why-a-timeout-was-not-enough"></a>

### タイムアウトだけでは不十分だった理由

`subprocess.run(..., timeout=...)` が kill するのは直接の子プロセスだけです。
`claude` と `codex` は自分の子プロセス（ripgrep、node、git）を起動し、それらは
生き残ります。さらにその後 `communicate()` を呼び出し、生き残った孫プロセスが
まだ保持しているパイプの EOF を待つため、タイムアウトの仕組みそのものが、
対処するために存在するはずの障害で永久にブロックする可能性がありました。
`tests/test_execution.py` は実際の孫プロセスを使ってこの状況を再現し、
呼び出しが数秒で戻ることを検証しています。

現在、実行は `orchestrator/execution.py` を経由します。これは子プロセスに専用の
プロセスグループを与え、超過時にはグループ全体を kill し（Windows では
`taskkill /T`、それ以外では `killpg`）、放棄可能な daemon スレッドで出力を
読み出します。diff をインライン化したレビュープロンプトはパイプバッファの
数倍の大きさになるため、stdin は専用のスレッドから書き込まれます。検出のために CLI に
尋ねる短い問い合わせ（`--version`、`--help`、`agy models`、`codex debug models`）も
同じ経路を通るので、そうした問い合わせが起動した補助のプロセスのせいで `doctor` や
実行前の確認が止まることもありません。

CLI が正常に終了しても、出力を握ったままのプロセスを残していった場合（たとえば
実装役がバックグラウンドで起動した開発サーバー）も同じです。読み取りスレッドには
数秒だけ終わる時間を与え、まだ読み取りで止まっているパイプは閉じません。どの
プラットフォームでも、閉じる処理がその読み取りスレッドを、つまりパイプを握る
プロセスを待ってしまうためです。それ以降、読み取りスレッドは読んだものを捨てる
ので、書き続けるプロセスがいっぱいのパイプで止まることも、メモリを埋めることも
ありません。CLI の終了後にそのプロセスが書いたものは実行の出力に含めず、その量を
警告で示します。そのうえで残ったものを止めます。POSIX では超過時と同じように
そのプロセスグループにシグナルを送り、止めたことを警告します。Windows では CLI が
終了した後はそこへ届かない（`taskkill /T` には親プロセスが必要）ため、そのまま
残し、`orphans_possible` を立てて確かめるよう警告します。どちらの場合も CLI の
終了コードはそのまま使います。

<a id="two-deadlines-because-slow-and-wedged-differ"></a>

### 2 つの期限（「遅い」と「固まった」は違うため）

| 期限 | 設定 | 意味 |
| --- | --- | --- |
| 合計、`run` | `run.timeout_seconds.<role>`（implementer 3600、ほか 1800） | ロールの `run` 1 回の上限 |
| 合計、レビュー | `review.timeout_seconds` (1800) | 各レビュアーの上限: `review run` と `run <reviewer-id>` |
| アイドル | `review.idle_timeout_seconds` (300) | この時間出力がない → 固まった。レビュアーと読み取り専用の `run` |
| アイドル、書き込む `run` | 1200、`review.idle_timeout_seconds` の方が大きければそちら | 同じ判定を、ファイルを変えうる `run` に |

`--timeout` は 1 回の呼び出しに限ってどちらの合計も置き換えます。implementer に
1 時間あるのは、計測した implementer の実行が 30 分を超え、1 回は 1800s で
止められたからです。アイドル期限は共通のままです。これは沈黙を測るもので、
沈黙の長さはタスクの大きさでは伸びません。

ただしファイルを変えうる実行（implementer、review fixer、`run --mode implement`）
のアイドル期限は 1200 秒（20 分）で、`review.idle_timeout_seconds` の方が大きければ
そちらです。こうした実行はテストやビルドを走らせ、コマンドの実行中は Claude の
ストリームに何も出ないので、300 秒ではそれより長くかかるテストスイートのある健全な
実行が止められてしまいます。一方で期限をまったく当てないと、固まった implementer が
全体の期限の 1 時間まで黙って走り続けます。1200 秒はその間を取ったものです。
それより長く黙るコマンドは stall として止められ、固まった実行には 60 分ではなく
20 分で気づけます。`--idle-timeout` かロールの `options.idle_timeout` で別の値に
できます。

1 行そろった出力だけでなく、どんな出力も出力として数えます。点を打ち続ける CLI や、
進捗バーを描き直す CLI は沈黙していません。出力は 1 行ずつではなく、届いたとおりに
読みます。

役に立つのはアイドル期限の方です。動いているエージェントは出力を出し続け、
固まったエージェントは沈黙するので、stall が 30 分ではなく数分で表面化します。

**これが適用されるのは、正常な実行が実際にストリーミングする場合だけです。**
これは推測ではなく、計測したものです。

| コマンド | 最初の出力 | 実行中 |
| --- | --- | --- |
| `codex exec` | 11.5s の実行のうち 0.4s | 出力が続く（間隔 ≤3.5s） |
| `claude -p --output-format stream-json` | 6.5s の実行のうち 2.5s | 回答が始まるまで `thinking_tokens` イベント、その後は書き終わるまで何も出ない |
| `claude -p --output-format stream-json --include-partial-messages` | — | 回答を含めて間隔 ≤1.7s |
| `claude -p --output-format text` | **8.9s の実行のうち 8.1s** | 終わるまで何も出ない |
| `agy --output-format stream-json -p` | すぐ（`init` とプロンプトのステップ） | ツールのステップと回答の断片ごとに 1 行。モデルが考えている間は何も出ない（12s の実行で間隔 ≤6s） |

`thinking_tokens` イベントはモデルが回答を書き始めると止まり、回答は書き終わった
ときにひとまとまりで届きます。17k 文字の回答では、そのためにストリーミング形式でも
191s の実行のうち 141s 何も出ませんでした。その 3 倍ほどの plan なら、正常なまま
300s のアイドル期限を越えます。そこで Claude の adapter は、`claude --help` に
フラグがあれば partial message も要求します。同じプロンプトで最大の間隔は 1.7s
でした。代わりに stdout は約 8 倍（そのときは 97 KB に対して 810 KB）になりますが、
adapter はこれまでどおり回答だけに絞ります。

text の行にアイドル期限を適用すると正常な実行を kill してしまうため、adapter に
アイドル期限を適用するには、その adapter が `streams_progress = True` を宣言して
いなければならず、しかもそれは根拠がある場合に限ります。適用されない場合は
合計期限だけが保護になります。だからこそ、以下の可観測性が重要なのです。

agy には、長い実行を測るまでアイドル期限を設けません。そのストリームはツールの
動きを報告しますが、最後ではないモデルのステップは終わったときに 1 行出すだけ
なので、ツール呼び出しの引数を生成している間（大きな `write_to_file` も含む）は
何も出ません。しかも測ったのは短い実行だけです。止まった agy の実行は、合計期限で
初めてわかります。

kill された実行は単なる失敗ではなく `stalled` として報告され、プロセスグループが
完全に終了しなかった場合は、孤児プロセスが残っている可能性があると警告されます。

どちらの期限も `time.monotonic()` で測ります。この時計は Windows ではスリープを
数え、Linux と macOS では数えません。そのため Windows では、スリープ中に期限を
過ぎた実行はマシンの復帰時に止められ、それ以外ではスリープの間は期限も待ちます。
実行時間予算はどのプラットフォームでもスリープを除きます。
[実行時間予算が数えるもの](#what-the-runtime-budget-counts) を参照してください。

<a id="seeing-a-stall-from-outside"></a>

### 外から stall を見る

ブロックしたオーケストレーターは自分自身を救えないため、ステージは開始
*前に*、期限と pid とともに記録されます。

```bash
dev-orchestra status          # in another terminal, or after a crash
```

これにより、完了時のみのログでは得られない 3 つのことがわかります。

* 期限を大きく過ぎてもまだ実行中のステージ
* プロセスが**消えた**ステージ — 結果を記録せずにクラッシュしたもので、
  以前はまったく痕跡を残さなかった、沈黙のケースです
* オーケストレーター自身が死んだ後の正確な状況

`status` を読むと、プロセスが消えたエントリーが消去されて `abandoned` として
記録されるので、それらは永久に実行中に見えるのではなく `state show` に
表示されます。

<a id="budgets"></a>

## 予算

アクションによって強制され、**終了コード 3** で拒否されます。

| 制限 | 設定 | 強制するもの |
| --- | --- | --- |
| レビューラウンド数 | `review.max_review_iterations` (2) | `review run` |
| 設計レビューラウンド数 | `review.design.max_iterations` (2) | `review run --design` |
| 変更サイズ | `review.context.max_chars` (400,000 chars) | `review run`、`review run --design` |
| ステージごとの試行回数 | `budgets.architect` (3)、`.implementer` (5)、`.review_fixer` (4)、`.test` (8) | `run <role>`、`budget consume <stage>` |
| ワークフロー内の委譲実行回数 | `budgets.total_delegated_runs` (40) | すべての `run` |
| 委譲実行時間 | `budgets.max_runtime_seconds` (14400) | `run <role>`、`review run`、`review run --design`、`budget consume` |

終了コード 5 は予算ではありません。`run implementer` は `design approve` を
待ちます。`references/workflow.md` を参照してください。

ラウンド予算が拒否するのは次のレビューであり、上限に達したラウンドの後の
改訂や修正ではありません。そのラウンドの指摘はもう一度 plan に反映されるか、
修正されて再テストされ、その後で初めて `status` が停止を告げます。同じ理由で、
使い切った試行予算が `status` の理由になるのは、そのステージがまだ必要な間だけ
です。`architect` は plan がない間だけ、`review_fixer` は最後のラウンドの修正が
まだ行われていない間だけです。

最後の 2 つは、委譲を行うサイクルのための安全網です。試行を消費するすべての
実行 — `run <role>` と `budget consume <stage>` — は前者に、計測値を持って
終わりまで到達したすべての実行は後者に計上されます。何も委譲しないサイクルは
どちらによっても制限されません。このツールが把握しているサイクルを止めるのは、
上記のラウンド、試行、進捗なしのルールです。

`review.context.inline_chars` がこの表にないのは、何も拒否しないからです。
これを超えると変更本体はファイルとして渡され、ラウンドは `partial` として
記録されます — [プロンプト内の変更本体](#the-change-body-in-the-prompt) を
参照してください。

実行時間は各実行が生成する計測値から計上されるため、計測値を記録する前に
kill された実行 — `jobs cancel`、Ctrl-C、OOM kill — には何も計上されません。
`run <role>` では、子プロセスが起動する前に試行 1 回と委譲実行 1 回を消費する
ので、最初の 2 行がそれを抑えます。レビュアーの実行はどちらも消費せず、ラウンドは
ラウンドが統合されたときにのみ進みます。同じスナップショットの再試行は同じ
ラウンドに留まります。したがって、統合前に kill された `review run` や
`review run --design` は、何によっても制限されません — ラウンド予算でも、
委譲実行回数でも、実行時間でもありません。

`run` と `review run` は自分の予算を消費します。オーケストレーター自身が行う
ステージ — とりわけテストスイートの実行 — は自分で予算を申告しなければなりません。

```bash
dev-orchestra budget consume test     # exit 3 when spent
dev-orchestra budget show
dev-orchestra budget reset            # start the budgets again
```

`budgets.session_idle_reset_seconds`（6h）の間アイドルだった台帳は終了した
ワークフローとして扱われるため、誰かがリセットを覚えていなくても、次の
リクエストは予算が満タンの状態で始まります。

どちらのリセットも、消去するのは予算だけです。`tokens show` の背後にある
トークン勘定は引き継がれます。これは残りいくら使えるかではなく作業にかかった
コストを記録するものであり、これを消去すると、6 時間中断したワークフローが
中断前の実行を無料として報告してしまったからです。したがって、勘定はワークフロー
全体を、それが経たすべてのリセットをまたいでカバーし、どのリセットでも消去
されません。消去するのはワークフローの削除（`workflow remove`）だけです。

勘定を分けるということは、ワークフローを分けるということです。
`dev-orchestra --workflow <id>` は作業に専用の `.ai/workflows/<id>/` を与え、
したがって専用の台帳、予算、勘定を与えます。

`--force` は拒否を上書きします。これは上書きすると決めた人間のためのもので、
スキルはオーケストレーターに対してこれを使わないよう指示しています。

<a id="a-change-too-big-to-review"></a>

### レビューするには大きすぎる変更

`review.context.max_chars`（400,000）は、1 つのラウンドがそもそも送る変更本体の
上限です。コードラウンドでは diff、設計ラウンドでは plan **とそれが答える
リクエスト**です — どちらもすべてのレビュアーのプロンプトにそのまま入るため、
plan だけを計測すると、形式上の理由でラウンドが上限を通り抜けてしまいます。
これを超えると、`review run` はどのレビュアーも開始する前、ラウンドが計上される
前、そして — 設計パスでは — plan が凍結される前に終了コード 3 で終了するので、
前のラウンドのレポートとトリアージは拒否の後も残ります。

400,000 文字はおよそ 100k トークンです。200k のウィンドウの半分を変更だけに
使うことになり、このリポジトリでこれまでに記録された最大のプロンプト
（99,814 chars）の 4 倍です。**デフォルトは、ここで誰かが実行したものを何も
拒否しません。** 単位が文字なのは、他のすべてがその単位で計測している
（`inline_chars`、`prompt_chars`）からであり、また標準ライブラリではトークンを
数えられないからです。換算は一定ではありません。CJK の多いテキストは 1 文字あたり
2〜4 倍のトークンになるため、同じ予算でもその分だけ緩くなります。

これは切り詰めではなく拒否です。収まるように hunk を削ると、レビュアーには判断
できない変更を渡すことになります — どの部分が一度も示されなかったかは出力の
どこにも書かれません — そのため、ツールは不完全なレビューを完了と呼ぶ代わりに
*レビューされていない*と伝えます。上限内に収める方法はすべて人間が行うものです。
`--base <rev>`、`review.exclude`、変更の分割、あるいはより短い plan です。

**`--force` は人間のものであり、自動化されたワークフローでは、レビューが一切
実行されないことを意味します。** スキルはオーケストレーターに、拒否を報告して
停止するよう指示しているので、`max_chars` を超える変更は何もレビューされない
まま実行を終え、オーケストレーターはそれを報告します。`status` は、ラウンドが
実際にその変更をレビューするまで `stop-and-report` と答えます — 後の拒否でも、
記録上の操作でもこれは解除されません — そのため、以前のラウンドのクリーンな
統合が、この変更がレビューされたものと取り違えられることはありません。

人間が実際に強制した場合、ラウンドは実行され、そのすべての記録にその旨が
残ります。各レビュアーエントリーと `consolidated.json` の `snapshot` ブロックの
`over_budget`、`consolidated.md` の `Change:` 行、そして `review status` の
1 行です。約束して**いない**のは、強制するとすべてのレビュアーが `partial` に
なるということです — それはこの設定ではなく `review.context.inline_chars` に
依存します。デフォルトでは 2 つは同じ数値なので、`max_chars` を超えるものは
インライン上限も超え、実際にファイルとして渡されます。これは出荷時の設定に
関する事実であってコードに関する事実ではありません。`inline_chars` を
`max_chars` より大きくするか、`max_chars` をそれより小さくすると、強制された
ラウンドは予算超過でありながらインラインで渡されます。拒否メッセージは、
目の前の変更に 2 つのどちらが当てはまるかを示します。

<a id="the-change-body-in-the-prompt"></a>

### プロンプト内の変更本体

`review.context.inline_chars`（400,000）は、変更本体のうちどれだけをレビュアーの
プロンプトに入れるかです。これ以下なら本体はインライン化され、ラウンドは
クリーンになり得ます。これを超えると、代わりに凍結されたスナップショットの
パスがレビュアーに渡され、何が返ってきてもラウンドは `partial` として記録されます
— 判定を回答から取れない理由については [Coverage](reviews.md#coverage) を
参照してください。

デフォルトは意図的に `max_chars` と一致させています。以前の値 120,000 には
計測上の根拠がありませんでした。プロンプトは stdin で CLI に届くので、argv の
長さは関係しません。本体をファイルとして渡すことで得られるのは、このツールが
検証できないレビューです。そのため、デフォルトではそれは人間が求めた場合に
のみ起こり、出荷時の動作は境界が 2 つではなく 1 つになっています。

`max_chars` より小さく設定すると、2 つの間に帯域ができます。そこに入るラウンドは
実行され、ファイルとして渡され、`partial` として記録されます。これは非常に大きな
プロンプトにコストを払わないと決めた人の明示的な選択であり、`partial` はその
代償です。`max_chars` より大きく設定すると、ファイルでの受け渡しは予算を超えて
強制されたラウンドでのみ起こり得ます。どちらも検証を通り、どちらも誤りでは
ありません。

すべてのラウンドは、計測の基準にした数値を記録します — 各レビュアーエントリーの
`inline_chars`、`consolidated.json` の `coverage.inline_chars` — `partial` の
ラウンドとサイズだけでは、それが大きな変更だったのか低い上限だったのかが
わからないからです。

<a id="surrounding-context-within-the-budget"></a>

### 予算の範囲内の周辺コンテキスト

`review.context.surrounding: enclosing` は、各コードレビュアーに diff に加えて、
各 hunk を囲む Python の関数・メソッド・クラスを渡します
（[周辺コンテキスト](reviews.md#surrounding-context) を参照してください）。
1 つのスナップショットで計測したところレビューが安くならなかったため、デフォルトでは off です
（[周辺コンテキストの効果を測る](#measuring-what-surrounding-context-does) を参照してください）。

追加される量には上限があり、その上限は上の 2 つの上限に上乗せされるのではなく、
そこから差し引かれます。

```
budget = min(surrounding_chars, max_chars - change_chars, inline_chars - change_chars)
```

したがって diff とそのコンテキストを合わせても、`max_chars` と `inline_chars` を
超えることはありません。コンテキストを on にしても、diff だけなら実行されたはずの
ラウンドが拒否されることはなく、インライン化されていた diff がファイル渡しに
なることもありません。`review.context.surrounding_chars` のデフォルトは 15,000 です。
1 つのスナップショットで計測したところ、実行あたりの費用は変わらず、60,000 では
渡した分がそのまま上乗せされました。収まらなかったものは黙って
落とされるのではなく、名前を挙げて除外されます。

採用したコンテキストは `max_chars` が計測するものに数えられます。各レビュアー
エントリーの `budget_chars` と `snapshot.budget_chars` は diff に、採用した
コンテキストをプロンプトに載る形で（`context_chars`：ソースと見出し・フェンス・
注記）足したもので、拒否が示すサイズも同じです。受け渡し方法、そして
それに伴う coverage は、引き続き diff だけで決まります。

シンボルはスナップショットの取得時に、diff の*前に*書き出した git のツリー
オブジェクトから抽出し、その後の作業ツリーからは決して読みません。設定が on の
ときは、`review.incremental_rounds: false` でもこのツリーを書き出します。この設定が
意味するのは引き続き「次のラウンドは修正だけに絞り込まない」ことだけで、
スナップショットのメタデータの `tree` は空のままです。作業ツリーに対して diff を
取ったラウンドでは、その後、抽出に使った各ファイルをハッシュし（`git hash-object`。
index を通らないので、未追跡ファイルを削除されたものと取り違えません）、ツリー内の
blob と比べます。その間に編集されたファイルは `changed while the snapshot was taken`
として除外され、プロンプトで名前が示され、スナップショットを取り直せば解消します。

<a id="measuring-what-surrounding-context-does"></a>

### 周辺コンテキストの効果を測る

`optimization report` の分割は、コンテキストあり・なしのラウンドを*異なる*変更
どうしで比べます。1 つの変更での効果を見るには、同じ凍結済みスナップショットを
2 回 — コンテキストなしで 1 回、ありで 1 回 — レビューします。そのとき
`review.context.surrounding` を変えない 1 回限りの上書きを使い、そのペアを読みます。

始める前に: 設定はデフォルト（`none`）のままにし、2 回の間に設定を変えないこと。
両回とも同じパネルで走らせること（`--only` を使うなら同じ引数で）。`--context` は
両方に同じものを渡すか、どちらにも渡さないこと。**トリアージの前に**行うこと。
そして**変更全体のラウンド** — 変更の最初のラウンド、またはクリーン / 全却下の
レビューの後のラウンド — で行うこと。incremental ラウンドは拒否されます。
**必ず手順 1 から始めてください**: コンテキスト付きで凍結されていない
スナップショットでは `--surrounding enclosing` が拒否されます。

```bash
# 1. Freeze the change and its candidates (even with the setting at none). The pair starts here
dev-orchestra review snapshot --surrounding enclosing
#    note "sha256 <12 chars>" and "context:  enclosing -- N symbol(s)"

# 2. Control: no context. The pair's first run, so its signature is registered as usual
dev-orchestra review run --surrounding none

# 3. Treatment: the same snapshot with context. The round does not advance; no signature is registered
dev-orchestra review run --surrounding enclosing
#    "Surrounding context: N symbol(s), X chars adopted (--surrounding enclosing for this run)"
#    exit 2 before any cost if nothing would be adopted (not frozen, no candidates, file delivery, no budget)
#    exit 2 if a finding was triaged or given a note after step 2

# 4. Read
dev-orchestra optimization report          # the "Paired on one snapshot" block
dev-orchestra optimization report --json   # paired.pairs[*], paired.delta
```

- 手順 2 と 3 は逆でも構いません。どちらの順でも、1 本目が findings の署名を
  登録し、2 本目 — 同じスナップショットの再実行 — は登録しません。その後の
  トリアージが扱うレポート（`reports/*.md` と `consolidated.*`）は最後の run の
  もので、次のラウンドと比べられる署名は 1 本目のものです。
- 両方の run に `--surrounding` を付けてください。付けない run は `measurement` を
  記録せず、ペアになりません。
- **数値の意味。** *counted* なペア — 同じパネル、全 run が届いた（`ok`）、同じ
  プロンプト入力、実際にコンテキストが採用された — の `delta` だけが、
  コンテキストの効果として読めます。delta が負なら、そのペアでコンテキストが
  それだけ節約したということです。どれかを満たさないペアは理由付きで一覧に
  載り、合計からは外れます。
- **言えないこと。** 1 ペアは 1 回の観測です。レビュアーは同一の入力でも run ごとに
  揺れ、ここではそれを揃えていません。数値で何かを決める前に、異なる 3〜5 個の
  変更でペアを取ってください。Codex はツールの利用を報告しないので、ツール系の
  数値は報告した run（Claude と agy）だけのものです。agy は呼び出しを数えますが
  その出力は数えないので、run あたりの出力文字数は出力を報告した run の数で
  割ります。
- **費用。** 1 ペアはそのスナップショットのパネルを 2 回走らせます。課金トークンと
  実行時間予算（`charged_seconds`）は、それぞれの run で実測された値がそのまま
  積まれます。2 本のプロンプトも所要時間も違うので、合計は正確に 2 倍には
  なりません。実際の値は `review run --json` の `usage` と、ペアの `with` /
  `without` で読んでください。`review run` 自体は `review` の試行回数を消費
  しませんが、毎回の run の前に `budget consume review` を呼ぶ手順なら、run ごとに
  1 回消費します。1 本目が `budgets.max_runtime_seconds` の残りを使い切ると、
  2 本目が拒否されることがあります。
- **変更全体のラウンドに限る理由。** incremental ラウンドのプロンプトには、
  その run の時点で accepted な findings（"The fix was meant to address:"）が
  `consolidated.json` から載ります — そして 1 本目がそれを書き直します。2 本の
  run はコンテキスト以外でも違ってしまうので、そこでは `--surrounding` を課金前に
  拒否します。
- **必ずスナップショットから始める理由。** 前回のレビューに accepted な finding が
  あり base が同じ incremental ラウンドでは、スナップショットは前回ラウンドの
  ツリーとの diff になります。そこで `--surrounding enclosing` で取り直すと、その
  ツリーが作業ツリーと一致するので全体の diff に戻り、sha256 が変わります。
  クリーン / 全却下のレビューの後は元から全体の diff なので、sha256 は変わりません。
  どちらの場合も、凍結の無いスナップショットでは enclosing の run が拒否されるので、
  手順は手順 1 から始めます。
- **2 本の間に予算がリセットされたとき。** `budget reset` やアイドルリセットは
  レビューの lineage を変えるので、2 本目はラウンド 1 から数え直し、
  `rerun: false` を記録して署名を登録します。ペアはそれでも成立し — 鍵は
  workflow ディレクトリとスナップショットで、予算の epoch ではありません —
  `--json` の `epoch` に 2 つの値が出ます。1 本目の後に finding がトリアージ
  されていれば、2 本目はそれでも拒否されます。同じ findings を組み立て直すうえ、
  トリアージは lineage に関係なく finding のキーで引き継がれるからです。
- **`--iteration` の明示。** 1 本目が記録したのと別のラウンドを `--iteration`
  で指定した run は独立したラウンドです。`rerun: false` を記録し、署名を登録します。

**計測した結果。** 4 つの変更（3,669〜91,562 文字）で、合計に数える 13 ペアを
取りました。パネルは両側とも Claude と Codex です（issue #130）。最大の変更の
対照側の run は、課金トークンが run ごとに約 5.6% 揺れ、Claude のツール出力は
最大 3.7 倍違いました。`surrounding_chars` が 15,000 のとき、平均の差はどの大きさの
変更でも ±6% 以内で、この揺れの中に収まりました。60,000 では、最大の変更で約
57,000 文字が採用され、2 ペアとも実行あたり 29% 増えました。渡したコンテキストの
分とほぼ同じです。どの設定でもレビューは安くならなかったので、コンテキストは off の
まま、上限は 15,000 とし、[周辺コンテキスト](reviews.md#surrounding-context) の
優先順位 2〜6 は進めません。

<a id="what-the-runtime-budget-counts"></a>

### 実行時間予算が数えるもの

実行自身が計測した、委譲実行の秒数です — ワークフロー開始からの経過時間では
決してありません。

**数えるもの。** 委譲した各子プロセスの生存時間で、実行ログに
`duration_seconds` としてすでに表示されているのと同じ計測値から、その間に
マシンがスリープしていた時間を引いたものです。レビューラウンドはパネルメンバーごとに数えられます。3 人のレビュアーがそれぞれ
25 分並列に実行すると、75 分を消費します。期限で kill された実行、失敗した実行、
stall した実行は、いずれも費やした分を費やしており、すべて計上されます。

**数えないもの。** オーケストレーター自身の作業、テストスイート、人間が考えて
いる時間です。何も委譲しない対話セッションはこの予算を一切消費せず、この予算に
よって制限もされません。まだ実行中の実行も数えません — 終了したときに計上される
ので、`budget show` は連続的ではなく段階的に変化します。結果を記録する前に
ラッパープロセスが死んだ実行 — `jobs cancel`、Ctrl-C、OOM kill — も数えません。
誰も計測していないので誰も請求せず、その形の暴走を制限するのは
`budgets.total_delegated_runs` とステージごとの試行予算だけです。

**スリープ**も数えません。デタッチした実行の途中で閉じたノート PC は、閉じている
間は何も実行していません。その測り方はプラットフォームによって異なります。実行を
測る時計である Python の `time.monotonic()` が、あるプラットフォームではスリープを
数え、ほかでは数えないためです。

| プラットフォーム | `duration_seconds` | 計上から除くもの | `suspended_seconds` |
| --- | --- | --- | --- |
| Windows | スリープを含む | `duration_seconds` から、スリープ中は止まる `QueryUnbiasedInterruptTime` でのその実行の増分を引いたもの | 0 でないときに書く |
| Linux、macOS | スリープを含まない（時計が止まる） | なし（除くべきスリープが入っていない） | 書かない |

したがってどのプラットフォームでも `charged_seconds` は `duration_seconds` から
`suspended_seconds` を引いたもので、スリープしなかった実行はちょうどその所要時間が
計上されます。この測り方から来る帰結が 2 つあります。

* 1 秒未満の差はスリープとは読みません。割り込み時間の時計はタイマーの 1 刻み
  （約 15.6 ms）ごとにしか進まないため、はるかに細かい `time.monotonic()` とは
  どの実行でも少しずれます。それより短いスリープは計上されます。
* Modern Standby は従来のスリープ状態ではなく、その間に割り込み時間の時計が
  止まるかどうかは文書化されていません。スタンバイの時間の一部は計上されることが
  あります。

除いたスリープは `suspended_seconds` として、実行イベント、レビューイベントの各
レビュアーのエントリー、デタッチした実行のジョブに記録されます。予算のエポック
ごとに合計され、実行時間予算とともにリセットされます。`budget show` と `status`
は、除いたスリープがあったときに限り、その量を示す行を加え、`--json` では
`runtime.suspended` として出します。計上と同じく、この数値は実行ごとに合算
されます。2 人のレビュアーが同じ 10 分間スリープしていれば 20 分になるので、
これはマシンがスリープしていた時間ではなく、委譲した実行時間のうちスリープして
いた分です。

`duration_seconds` 自体は変わらず、そこから作るレポートも変わりません。Windows
でだけ、`optimization report` は実行時間にスリープを含めます。また `status` は
実行中のステージを実時間で期限と比べるため、スリープした実行はそれが終わるまで
"Stalled stages" に並ぶことがあります。この行は助言にすぎず、プロセスがまだ
生きているステージが片付けられることはありません。

並行作業は合算されるため、**合計は実時間を超えることがあります**。これを設計
する際に計測したワークフローでは、自律的なものは自身の実時間の 1.23〜1.45 倍に
なり、最も重いものは委譲実行が 5619s に達しました。

**ワークフローが上限をどこまで超え得るか。** 拒否は実行の開始前に起こり、実行中に
起こることはなく、実行中の作業は数えられません — したがって超過分は、最後の
チェックを通過した後に始まったすべてです。`D` をエントリーに記録された期限
（`--timeout`、なければ実行には `run.timeout_seconds.<role>`、レビュアーには
`review.timeout_seconds`。どちらも上限はありません）、`G` を kill の猶予と
出力の読み出し（`KILL_GRACE_SECONDS` の 5s に少し足したもの）とすると、次の
ようになります。

```
overshoot ≤ Σ over in-flight runs (D + G)  +  Σ over in-flight review batches N × (D + G)
```

`N` はバッチに*受け入れられた*すべてのレビュアーで、まだ待機中のものも含みます。
パネルは同時に最大 8 つまで実行し、バッチ内には予算チェックがないため、2 回目の
波に入った 9 人目のレビュアーも期限まで実行されます。ステージを 1 つずつ進める
場合、これは 1 回の実行（≤ 1805s、implementer なら ≤ 3605s）または 2 レビュアーのラウンド 1 回
（≤ 3610s）です。デタッチしたワーカーを重ねると、それぞれ項が 1 つ増えます。

これが計測に基づく予算になる前に書かれた台帳は、ゼロから始まります。その台帳が
記録していたのは実時間であり、そこから計測値を再構成するのは計測値をでっち上げる
ことになるからです。

<a id="what-a-delegated-runs-tool-activity-can-and-cannot-say"></a>

### 委譲実行のツール活動からわかること、わからないこと

ここには委譲したエージェントが読むものを制限する仕組みはありません — どの
CLI もそれに対する制限を受け付けません — が、Claude の実行については、すでに
ストリーミングしているイベントから事後に数えることができます。`tokens show` と
`optimization report` は、実行ごとに 2 つの数値を報告します。ツール呼び出しの
回数と、それらのツールが出力した文字数です。agy の実行は前者を報告し、後者は
報告しません。そのストリームはツールのステップごとに名前を出しますが、ツールが
返したものは要約（`4 lines, 17 bytes`）しか出さないからです。

**`Read` だけでなく、すべてのツール呼び出しを数えます。** Claude の読み取り専用の
実行が持つのは `Read`、`Grep`、`Glob` だけで — `Bash` はありません — `Grep` と
`Glob` も `Read` と同じようにファイルを読みます。implement の実行はすべてのツールを
持ちます。これを設計する際に計測した唯一の実行は、Claude の読み取り専用の実行が
この 3 つに絞られる前のもので、
`CONTRIBUTING.md` の行数を報告するよう求められ、`Bash`（`wc -l`）でそれを行い、
一度も `Read` を呼びませんでした — `Read` だけを数えていたら、そのレビュアーは
何も開かなかったと記録されていたでしょう。

**文字数は観測されたツール出力であり、読んだソースではありません。** 同じ
`wc -l` は 200 行のファイルに対して 3 文字を返しました。同じファイルに `cat` を
使えば全体を返していたはずです。CLI の外からはこの 2 つは区別できないので、
**委譲実行が実際にどれだけのソースを読んだかは、ここからは知り得ません**。
この数値はその代理指標であり、同じレビュアーの変更前後を比較するには有用ですが、
何を読んだかを述べるためのものではありません。

心に留めておくべき帰結が 3 つあります。

* **Codex はどちらも報告しません。** その adapter は最終メッセージをファイルから
  取り、使用量を散文のフッターから読みます。散文からツール呼び出しを数えると、
  CLI 自身の出力と同じくらい容易にレビュー対象のコードにもマッチしてしまいます。
  その実行は未報告となるため、実行ごとの数値はすべての実行ではなく、報告した
  実行の数で割っています。実行あたりの出力文字数は出力を報告した実行の数で割る
  ので、agy の呼び出しは実行あたりの利用回数には入り、実行あたりの文字数には
  入りません。agy だけが報告した場合、その数値は `-` と表示されます。
* **未報告はゼロではありません。** ツールを使わなかった実行は `0` を報告します。
  報告できなかった実行は何も報告せず、出力には `-` が表示されます。
  `options.output_format: json` に設定したロールは報告できません — その形式は
  `result` オブジェクトを 1 つ出力するだけで、ツールイベントを一切出しません。
  これらのカウントが存在する前に記録された実行も報告できず、カウントされた実行が
  その横に記録された後も報告できないままです。
* **イベントの形は CLI のものです。** その変更は誤った数値ではなく未報告へと
  劣化します。ユニットテストはフィクスチャを読むので、そのずれを検出するのは
  `scripts/smoke_live.py` です。

<a id="re-fetching-the-source-reported-as-tool-activity-not-counted-not-limited"></a>

### ソースの再取得: ツール活動として報告し、数えず、制限もしない

レビュアーに囲む関数を渡すのは、ファイルをもう一度開かずに済むようにするため
です。それが実際に効いているかは間接的にしか見えず、それについて言えることは
次がすべてです。

* **Claude のカウントは代理指標です。** `tool_uses`、`tool_uses_by_name`、
  `tool_output_chars` が数えるのは、ツール名ごとの呼び出し回数と、それらの呼び出しが
  返した文字数です。`Bash` 経由の `cat` と `Read` はどちらも 1 回で、同じファイルの
  2 回目の読み取りは 1 回目と区別できず、`wc -l` の 3 文字と `cat` のファイル全体は
  読んだ量を表しません。**プロンプトがすでに運んだソースの再取得は、これらの
  カウントからは見えません。**
* **agy のカウントは呼び出しだけです。** `tool_uses` と `tool_uses_by_name` は
  ツールのステップから取ります。出力の文字数はありません。
* **Codex には代理指標すらありません。** 使用量は散文のフッターから取っており、
  数えるべきツールイベントがありません。
* **何も制限していません。** adapter が渡すのは
  `--permission-mode plan --disallowed-tools Edit,Write,NotebookEdit --tools
  Read,Grep,Glob --strict-mcp-config --restricted`（Claude）と `-s read-only`
  （Codex）です。これは Claude の実行が*どう*、*どこで*読むか — `Read`、`Grep`、
  `Glob` で、作業ディレクトリと `--add-dir` の中で（claude 2.1.283 で絶対パスに
  ついて実測。シンボリックリンクは未検証）— を制限しますが、どれだけ読むかは
  制限しません。どちらの CLI にも、実行が行える読み取りの回数や文字数を制限する
  フラグは渡しておらず、CLI が受け付けるかもしれないという推測でフラグを足すことも
  しません。

したがって、このツールは代理指標を報告するだけで、再取得を数えることも禁じる
こともしません。読み取りを減らすためにこのツールが持つ唯一の手段は、レビュアーが
必要とするコンテキストを渡すこと — それが[周辺コンテキスト](reviews.md#surrounding-context)
です — であり、それが効いたかどうかを見る方法は、コードラウンドをコンテキストを
運んだものと運ばなかったものに分ける `optimization report` です。**比べるのは
実行あたりの行で、生の行ではありません。** 生の課金とツールの数値は、変更ごとの
大きさとパネルのレビュアー数に連動して動きます — 小さな変更はレビュアー 1 人に
削減されるのが普通です — そのため各群には、実行あたり・変更 1k 文字あたりの値も
示されます。各ラウンドのサイズは、その数値を報告した実行数で重み付けされます。

<a id="no-progress"></a>

## 進捗なし

予算はいずれループを止めます。結果の繰り返しは、それが無意味だったことを
即座に証明し、これはより早く、より正確です。

```bash
dev-orchestra progress record test --signature "3 failed: test_a, test_b, test_c"
```

同じシグネチャが 2 回続くと、直前の修正が何も変えなかったことを意味し、その
ステージに対する次の `budget consume` は拒否されます。*異なる*シグネチャは
カウントをリセットします。何かが動いたからです。

レビューは、未解決の指摘の集合から自動的に自分のシグネチャを登録します。同一の
ラウンドは出力で指摘され、ここで数えられるので、修正者が何も達成しなくなると
レビュー→修正→レビューは止まります。ラウンドの上限では、繰り返しは最後の
ラウンドの改訂や修正と再テストを止めません -- 節約すべき再レビューは残って
いないからです -- そのため、`status` はそれらが終わってから初めてこれを理由として
示し、その間は `identical_rounds` を報告します。

`budgets.max_repeats_without_progress`（2）がしきい値を設定します。

<a id="not-blocking-in-the-first-place"></a>

## そもそもブロックしない

期限は被害を限定しますが、呼び出し元が待つことを止めはしません。委譲実行の
進行中、オーケストレーターはその呼び出しの中にいるので、状況を報告することも
それに対処することもできません。デタッチすれば構造的にこれを解決できます。

```bash
id=$(dev-orchestra run implementer --prompt-file plan.md --detach --json | jq -r .id)
dev-orchestra jobs wait "$id" --timeout 120     # exit 4: still running
dev-orchestra status                            # meanwhile, visible from anywhere
```

最悪のケースは、際限のないブロックではなく、上限のある待機と明確なステータスに
なります。結果を記録せずにワーカーが死んだジョブは、実行中台帳が行うのと同じ
突き合わせによって `abandoned` として報告されます — 死んだワーカーが、まだ
作業中のワーカーのように見えてはなりません。

デタッチは任意です。ポーリングごとに 1 往復のコストがかかるので、すべての呼び出し
ではなく、長いステージ（実装、大きなレビュー）に使う価値があります。

上限のある待機でも、ユーザーは何分も何も見えないままになります。そこで待機のたびに、
ジョブが何をしているかも示します。実行中、`jobs wait` と `jobs show` は経過時間を表示し、
CLI がツールを使い始めてからは、ツール使用の回数と **コンテキストトークン**（モデルが最後に
見たコンテキストの大きさで、累計ではありません）、最新のツール行、`next:` カーソルも表示します。
`jobs wait <id> --since <n>` は新しいものだけを並べ、`--activity <m>`（0 から 100）は何行並べるかです。
1 行に書くのはどのツールかと、許可リストを通した対象だけです。プロジェクトからの相対パス、
プログラム（`git` など一部はサブコマンドも）、URL のホストです。モデルのテキストやツールの自由記述の引数は
決して表示せず、どの行も書き込む前と読むときに切り詰め、制御文字を除き、伏せ字にします。
ファイルは 500 行を超えるとローテートするので際限なく大きくはならず、番号の抜けは捨てられた行として
報告されます。オーケストレーターがバックグラウンドで実行するレビューのラウンドでは、
`review run --progress` が同じ行を、ツール使用とレビュアーごとにタグ付きの 1 行として stderr に
出します。フラグ、JSON、許可リストは [CLI リファレンス](cli.md#jobs) にあります。

<a id="the-verdict"></a>

## 判定

`dev-orchestra status` は、これらすべてを 1 つの答えにまとめます。

```json
{
  "verdict": "stop-and-report",
  "reasons": ["review budget spent (2/2 rounds) with 1 finding(s) still open; fixed and re-tested after the last round, not re-reviewed -- report"],
  "stalls": [],
  "abandoned_stages": ["implementer"],
  "budgets": {"test": {"used": 8, "limit": 8, "remaining": 0}}
}
```

`continue` または `stop-and-report` と、その理由です。覚えておくべき 4 つの
ルールではなく参照すべき 1 つのコマンドであり — しかも仕組みなので、
オーケストレーターがこのページを読んだかどうかに依存しません。

<a id="feeding-it-a-lot-of-text"></a>

## 大量のテキストを渡す

ログ、レガシーモジュール、長い仕様書は、そのために設定したモデルにまとめて渡し、
*結論* だけを残して、design とレビューは生の山ではなくその結論から進めます。
40 MB のログに使ったコンテキストは、レビュアーが差分に使えなくなるコンテキストです。

解析の依頼はファイルに書き（中身を貼り付けるのではなく、リポジトリ内のパスを指します）、
`workflow show` の `Artifacts:` のディレクトリの下に `execution/analysis-request.md` として置いて、
大きなコンテキストを持つモデルに割り当てたロールで実行します。

```bash
dev-orchestra run orchestrator \
  --prompt-file .ai/execution/analysis-request.md \
  --output .ai/analysis.md
```

うまくいく依頼の例:

> `log/production-2026-09-08.log` と `app/services/checkout/*.rb` を読んでください。
> 失敗パターンの種類、それぞれの発生頻度、関係するコードパスを挙げてください。
> 修正はまだ不要です。finding だけを、グループに分け、`file:line` を付けて出してください。

そして、ログではなく要約から設計します。

```bash
dev-orchestra run architect --prompt-file .ai/analysis.md --output .ai/plan.md
dev-orchestra run implementer --prompt-file .ai/plan.md
dev-orchestra review snapshot --base main
dev-orchestra review run
```

仕様書のレビューや依存関係の監査でも同じ分担が使えます。1 つのモデルが消化し、
別のモデルが設計し、さらに 2 つが結果について意見を食い違わせます。

<a id="what-a-run-costs"></a>

## 実行にかかるコスト

委譲した実行はそれぞれ消費量を記録するので、「トークンはどこに消えたのか」という
問いには推測以外の答えがあります。

```bash
dev-orchestra tokens show
```

```
  stage              meas.     input    output     total    billed      cost
  architect            1/1     8,200     2,100         -    11,500   $0.0421
  implementer          1/1    21,300     8,400         -    31,900   $0.2140
  review               4/4    58,000     6,400         -    64,400   $0.3900
  ALL                  6/6    87,500    16,900         -   107,800   $0.6461

Per reviewer:
  claude-general       2/2    29,100     3,300         -    32,400   $0.1950
  codex-general        2/2    28,900     3,100         -    32,000   $0.1950
```

合計は `status` と `summary` にも出ます。各列の意味と、`meas.` と `billed` が何を
含まないかは [`tokens`](cli.md#tokens) にあります。読むときに大事なのは次の 2 つです。

- **推定は一切しません。** プロンプトだけから見積もると、子 CLI のシステムプロンプト、
  ツールスキーマ、CLI が自分で読んだファイル — 入力の大部分 — が抜け落ちるので、
  数字はすべて CLI が報告したものです。
- **レビュアーは 1 人ずつ数えます。** レビューはパイプラインで最も重複するコスト
  （同じ差分を、レビュアーごとに、ラウンドごとに）だからです。3 人目のレビュアーが
  元を取れているかは、レビュアーごとの行で分かります。

これは会計であって予算ではありません。かかるコストを理由に実行を拒否するものは
ありません。それは [予算](#budgets) の役目です。

<a id="how-hard-to-try-to-be-cheap"></a>

## どこまでコストを削るか

`optimization.level` は、レビュアーが動き出す前にレビューラウンドについて 3 つのことを
決めます。テストが失敗しているツリーをそもそもレビューするか、小さく低リスクな変更に
パネル全員を使うか、各レビュアーに何件の finding を求めるかです。レベルとその表、
キーは [最適化レベル](configuration.md#optimization-level) に、レベルがラウンドに
できることとできないことは
[レビューが実行されない場合、または縮小して実行される場合](reviews.md#when-a-review-does-not-run-or-runs-smaller)
にあります。コマンドラインでは次のように見えます。

```
$ dev-orchestra review run
refusing to review: the last recorded test run failed. Reviewing code that
does not pass its own tests spends a reviewer on a problem you already know
about. Fix the tests, record the result, and run again -- or pass --force.
```

ゲートが読むのは、直近の `dev-orchestra state record test ok|failed` が書いたものです。
結果が記録されていないツリーは、警告したうえでレビューされます。

```
$ dev-orchestra review run
note: aggressive → quality: db/migrate/003_drop_orders.rb matches *migrate*/*
```

高リスクの変更は、設定が何であれ `quality` にエスカレーションします。

```
note: low-risk change (1 file(s), 12 line(s)): 1 reviewer instead of the full
panel (claude-general). Cross-model disagreement is what a second reviewer
buys; raise optimization.level or the low_risk thresholds to keep it.
```

縮小したパネルには `general` のレビュアーが残り、そのことが表示されます。

<a id="did-it-work"></a>

### 効いたのか

```bash
dev-orchestra optimization report
```

レベルの効果は率です — 何回拒否したか、何回パネルを削ったか。そのためこのレポートは、
1 つのワークフローの `tokens show` ではなく、すべてのワークフローの run log を読みます。
出力、design レビューの消費が別に出ること、推定削減量が何であって何でないかは
[`optimization`](cli.md#optimization) にあります。

<a id="what-is-still-not-covered"></a>

## まだカバーされていないこと

上記の正直な限界です。

* **pid は再利用されることがあるため**、「プロセスが消えた」はベストエフォート
  です。ステージの pid はフラグ付けと消去に使われるだけで、kill には決して
  使われません。デタッチしたジョブのワーカーの pid は `jobs cancel` が止める
  対象でもあるため、ジョブは pid と一緒にワーカーの開始時刻を記録し（Windows と
  Linux）、止める前に照らし合わせます。pid がいまは別のプロセスのものなら、
  ジョブを abandoned にして、そのプロセスには触れません。開始時刻のない記録
  （以前のバージョンが書いたもの、または開始時刻を読まない macOS のもの）や、
  生きている pid の開始時刻がいま読めないときは、POSIX では pid がまだ自分の
  プロセスグループを率いている間（ワーカーはそうなっています）だけ止め、
  Windows では止めません。取り消しがそうした pid を動いたまま残したとき、
  またはワーカーそのものを止めたと確かめられなかったときは、ジョブを
  終わっていない状態のままにし（`workflow remove` は引き続きそれを待ちます）、
  exit 1 で終わります。
* **予算はプロジェクトのワークスペースごと**で、`.ai/state.json` をキーにして
  います。1 つのチェックアウト内で並行する 2 つのワークフローは予算を共有します。
* **ここには 1 人のレビュアーのトークン消費を制限するものはなく**、制限するのは
  実時間だけです。`review.context.max_chars` は*送る*ものを文字数で制限しますが、
  これはトークンとは別物であり、さらにレビュアーがその後自分で読みに行くものとも
  別物です。
* **レビュアーが読む量を制限するものはなく**、どれだけ読んだかも計測できません。
  Claude のレビュアーが読む手段は `Read`、`Grep`、`Glob` だけで、範囲は作業
  ディレクトリと `--add-dir` の中です。Codex のレビュアーは閉じ込められていません。
  上記のカウントはツール呼び出しとそれらのツールが出力したものです。`wc -l` と
  `cat` は同じファイルを読み、3 文字と全体をそれぞれ報告します。Codex はどちらの
  数値も報告しません。
* **stream-json の解析はイベントスキーマに依存しており**、そのスキーマは CLI が
  所有しています。失敗するのではなく劣化します — result イベント、次に assistant
  のテキストブロックと途中で切れたメッセージのストリーム済みテキスト、次に生の
  stdout — が、形式が変わると構造化された追加情報
  （`is_error`、`num_turns`）は失われます。
* **継続した architect のセッションも他の実行と同じく stall しうります**（`run architect
  --resume`）。アダプタが partial message を要求するので、長い plan を出力している
  だけでは stall に見えなくなりました。ただし、インストールされた CLI がそのフラグを
  示していなければ、最終メッセージを書いている間は何もストリームされません。stall または
  失敗した継続の実行は報告され、再試行されません。次の `--resume` は新規に走ります
  （`it did not succeed`）。新規にもう一度だけ実行されるのは、CLI がもう存在しないと言った
  セッションだけで、それには試行を 1 回使います。
* **`--resume` が継続するセッションの指定については `state.json` を信頼します。** plan の
  承認や予算について信頼しているのと同じです。それを編集できる人は、このマシンにある自分の
  別のセッションを architect に継続させられますが、そのセッションはもともと直接読めるものです。
  id は使う前、記録する前に UUID であることを確かめるので、コマンドラインにフラグを差し込む
  ことはできません。そこから読んだ値で繰り返されるのはこの確かめた id だけで、コマンドライン
  （`--print-command` が表示するもの）と、イベント、ジョブレコード、実行中のエントリの
  `resume.resumed_from` に現れます。
* **拒否されたセッションを見分けられるのは `stream-json` のときだけです。**
  `options.output_format: text` や `json` では、CLI の出力にセッションがなかったことを示す
  兆候がないので、そうした実行は通常の失敗として報告されます。
* **継続したセッションが読み取り専用のままかどうかは、CLI の版ごとに**
  `scripts/smoke_live.py` で確認するもので、常時確認しているわけではありません。確認した版より
  新しく、メジャー版が同じ版は信頼に基づいて継続するので、新しい版で継続した Claude のセッションが読み取り専用を
  失っても、その版でスクリプトを実行するまで気づけません。版の文字列が変わらないまま挙動が変わった
  場合も、スクリプトを再実行するまで気づけません。Codex の fork は実行後にその rollout から読み取り
  専用だったことを確かめます。これは書き込みを見つけますが、防ぎはしません。
