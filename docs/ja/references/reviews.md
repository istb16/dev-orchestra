# レビュー

<a id="the-rules-that-make-multi-model-review-worth-doing"></a>

## マルチモデルレビューを価値あるものにするルール

1. **凍結されたスナップショットは 1 つだけ。** すべてのレビュアーは、誰かが
   開始する前に取得された、まったく同じ diff を見ます。
2. **相互汚染を起こさない。** どのレビュアーも他のレビュアーの出力を見ません。
   独立した意見の相違こそが価値のすべてです。
3. **読み取り専用。** レビュアーは読み取り専用のサンドボックスで実行されます。
   コードを編集するレビュアーはバグです。
4. **部分的な失敗は普通のこと。** 1 つのレビュアーがタイムアウトしても、他の
   レビュアーの結果は無効になりません。
5. **指摘は主張であって事実ではない。** オーケストレーターがトリアージするまで、
   何も修正担当（fixer）には渡りません。

<a id="snapshot"></a>

## スナップショット

```bash
dev-orchestra review snapshot                 # working tree vs HEAD
dev-orchestra review snapshot --base main     # everything since main
dev-orchestra review snapshot --no-untracked  # tracked changes only
dev-orchestra review snapshot --no-exclude    # generated files included too
```

`.ai/reviews/review-target.diff` とメタデータを書き出します。

```json
{
  "strategy": "git diff HEAD",
  "base": null,
  "head": "9f2c…",
  "files": ["app/services/pricing.rb", "spec/services/pricing_spec.rb"],
  "untracked_included": ["app/services/pricing.rb"],
  "withheld": [
    {"path": "package-lock.json", "pattern": "package-lock.json", "added": 412, "deleted": 87}
  ],
  "exclude_patterns": ["*.lock", "package-lock.json", "dist/*", "..."],
  "bytes": 4213,
  "sha256": "…",
  "empty": false,
  "surrounding": {"mode": "enclosing", "path": ".ai/reviews/review-surrounding.json", "tree": "3f2a…",
                  "candidates": 7, "chars": 49371, "skipped": 3}
}
```

`surrounding` があるのは `review.context.surrounding: enclosing` のときだけです。
[周辺コンテキスト](#surrounding-context) を参照してください。

未追跡ファイルはデフォルトで含まれます（1 ファイルあたり 512 KB まで）。新しい
モジュールは、たいてい変更の中で最も重要な部分だからです。sha256 はすべての
レビュアーのレポートに刻印されるので、全員が同じものを判定したことを証明できます。

スキル自身のファイルがスナップショットに含まれることはありません。ワークスペース
ディレクトリ（`.ai/`）配下のすべてと、任意の `.dev-orchestra.yaml|yml|json` は
スキップされるため、セットアップウィザードが書き出したばかりの設定が、毎回の
レビューで「変更」として現れることはありません。

スナップショットの取得には git が必要です。空のスナップショットは非ゼロで終了します。
レビューするものが何もないということであり、通常は実装ステージが何も書き出さな
かったことを意味します。

<a id="withheld-files"></a>

### 本文を省略するファイル

レビュアーが diff を読むのは、誰かが書いたコードを判定するためです。ロック
ファイル、バンドル、記録されたスナップショットは人が書いたものではないのに、
実際のコードと同じだけトークンを消費します。しかもレビュアーごとに、ラウンドごとに
です。そのため、よくある依存関係の更新が、それに付随する変更そのものより高く
つくことが日常的に起こります。`review.exclude` は、そうした diff の*本文*を
省略します。400 パッケージのロックファイル更新と 2 行のソース変更を組み合わせて
計測したところ、レビュアー 2 人による 1 ラウンドの入力トークンは 44,783 から
1,711 に減りました。

省略は隠蔽ではなく、この区別こそが設計のすべてです。

- ファイル名は変更行数とともに引き続きレビュアーに伝えられるので、依存関係の
  バージョンが本当に問題になるレビューでは、レビュアーがそれを読みに行けます
- `review snapshot` は、何を省略したか、どのパターンによるものかを出力します
- `--no-exclude` を付けると、その 1 回はすべてを送ります
- 有効だったパターンはスナップショットのメタデータに記録されるので、スナップ
  ショットは後からでも自身の内容を説明できます

マッチングは fnmatch で、Windows で取得したスナップショットが Linux で生成される
ものと同じ内容になるよう、すべてのプラットフォームで大文字と小文字を区別します。
対象は 2 つあり、リポジトリ相対のフルパスと、`/` を含まないパターンの場合は
ベース名単独です。そのため `*.lock` はどの深さにあるロックファイルにもマッチします。
`*` は `/` をまたいでマッチします。デフォルトが、実装されていない `**` に頼らず
`dist/*` と `*/dist/*` の両方を明記しているのはこのためです。

デフォルトのリストは、ロックファイル、`dist/`、`vendor/`、`node_modules/`、
minify された出力、ソースマップ、`*.snap` をカバーします。曖昧なものは意図的に
外しています。`build/` は慣習的には出力先ですが、手書きのファイルが置かれることも
十分に多いため、デフォルトで除外すると実際の作業を隠してしまうことがあります。
実際の変更を黙って落とすことは、ロックファイルの分を支払うことより悪い失敗です。

変更されたファイルが*すべて*省略された場合、スナップショットは空になり、その旨を
そのとおりの言葉で伝えます。これは「何も変更されていない」とは別の状況であり、
`review run` は空の diff として報告するのではなく、ファイル名を挙げて
`--no-exclude` を案内します。

リネームは検出される（`-M`）ので、移動したファイルは長さの 2 倍ではなくヘッダー
1 つ分のコストで済みます。ただし、移動がステージされている必要があります。
ステージされていない `mv` は、git にとって削除と未追跡ファイルという 2 つの無関係な
事実になり、`git
diff` の観点からもそのように扱われます。

<a id="surrounding-context"></a>

## 周辺コンテキスト

```yaml
review:
  context:
    surrounding: enclosing      # none (default) | enclosing
    surrounding_chars: 15000    # the most it may add; null means the default
```

diff を渡されたレビュアーに見えるのは各 hunk の前後 3 行だけで、判断する前に
ほぼ必ず、その hunk が属する関数を自分で開きます — そのコストはレビュアーごと、
ラウンドごとに支払われ、ここからは見えません。`surrounding: enclosing` にすると、
その関数もプロンプトに入ります。diff の後ろに置かれ、変更の一部ではなく
コンテキストとして示されます。YAML では `off` は `false` として読まれ、`false` と
`null` はどちらも `none` を意味します。`true` はどのモードも指さないので拒否
されます。1 つのスナップショットで計測したところレビューが安くならなかったため、off で出荷
されています（[周辺コンテキストの効果を測る](limits.md#measuring-what-surrounding-context-does) を参照してください）。
`optimization report` が、これを使ったラウンドと使わなかったラウンドを比較します
（[optimization](cli.md#optimization) を参照してください）。

**スナップショットと一緒に固定されます。** `review snapshot` は diff を取ったのと
同じ git ツリーからシンボルを抽出し、diff の sha256 を刻印して
`review-surrounding.json` に書き出します。`review run` はそのファイルを読むだけ
なので、スナップショットと実行の間にファイルを編集しても、レビュアーに示される
ものは何も変わりません。設定が off のときに取ったスナップショットには固定された
ものがなく、設定を on にして実行すると、作業ツリーを読むのではなくその旨
— `not frozen: … take it again` — を伝えます。

**どのシンボルか。** 変更された各行は、新しい側の行番号の対です。追加された行 `n`
は `(n, n)`、削除された行は `n - 1` と `n` の間にあったので `(n - 1, n)` です。
両端を含む最小の関数・メソッド・クラスが、その変更を **encloses**（囲む）します。
どれもなければ、どちらか一方の端を含む最小のシンボルが **adjacent**（隣接）に
なります。削除がその縁にあり、残ったもののどれもそれを囲んでいない、ということ
です。A と B の間の関数を丸ごと削除すると、A と B は adjacent であり、囲んでいる
わけではありません。adjacent のシンボルは encloses のものの後に採用され、
`adjacent to a deletion, not enclosing it` と示されます。

すべての行が追加されたシンボルは候補になりません。diff がすでにその全体を
示しているからです。その変更は外側のシンボルに移ります。メソッドを追加したときに
クラスが候補になるのはこのためです。同じ理由で、新規ファイルは一切抽出しません。

**Python のみ。** `ast` を通した `.py` ファイルだけです。それ以外は抽出せず、
プロンプトでは `not python` として件数を示します。行の窓による代替はありません。
diff はすでに前後 3 行を運んでおり、関数の途中で切れる窓は囲むシンボルでは
ないからです — 誤解を招くコンテキストは、ないほうがましです。

**何も推測しません。** シンボルを正確に取れないファイルは、理由とともに
スキップされます。

| 理由 | いつ |
| --- | --- |
| `not python` | `.py` ファイルではない |
| `new file (the diff already shows all of it)` | この変更で追加された |
| `deleted` | この変更で削除された |
| `symlink`、`submodule` | ツリー内の symlink または gitlink — 決してたどらない |
| `file over 512,000 bytes` | 全体を渡すには大きすぎる |
| `not utf-8`、`syntax error` | 格納されたままの形では `ast` が読めない |
| `no enclosing symbol beyond the diff` | モジュールレベルのコードだけ、または新しいシンボル全体だけが変更された |
| `ambiguous path (x.py or b/x.py)` | 両方の名前がスナップショットにあり、diff のヘッダーからどちらかがわからない |
| `changed while the snapshot was taken -- take it again` | ツリーと diff の間に編集された（[limits](limits.md#surrounding-context-within-the-budget) を参照） |
| `not in tree`、`unreadable`、`no tree object (git write-tree failed)` | git がツリーからそのファイルを取り出せなかった |

`+++` のパスは、このツールが設定しない git の設定（`diff.noprefix`、
`diff.mnemonicPrefix`）に依存するので、接頭辞は仮定しません。リネームの
`rename to` 行が優先され、そうでなければ、書かれた名前と、その先頭 2 文字を
除いた名前のうちスナップショットが挙げているほうを使います。両方を挙げている
ときに限って、`diff --git` 行にどちらかを尋ねます。それでも決まらなければ、
両方のファイルを名前を挙げてスキップします。

**予算の範囲内で採用します。** `review run` の時点で、候補は encloses を先に、
次に adjacent を、それぞれの中では小さい順に採用します — 固定の予算で、最も多くの
hunk にシンボルが行き渡る順序です — 上限は
`min(surrounding_chars, max_chars - change, inline_chars - change)` です。予算は
プロンプトに載る形のブロック — 見出し・フェンス・除外一覧を含む — に対して
使われ、そのサイズは `context_chars` として記録されます。diff と
そのコンテキストを合わせてもどちらの上限も超えないので、これを on にしても
ラウンドが拒否されたり、インライン化されていた diff がファイル渡しになったりする
ことはありません。クラスとその中のメソッドが両方とも候補になることがあります。
メソッドが先に採用され、クラスは追加分がまだ収まる場合にだけ採用されます。
その場合メソッドはクラスに畳み込まれ、`includes` に名前が挙がります。すでに
採用したクラスの中にある、削除に隣接する（adjacent）メソッドも同じように
畳み込まれます — 同じものが 2 度示されることはありません。diff がファイルとして
渡されるラウンドは何も採用せず、すべての候補を `file delivery` による除外として
名前を挙げます。

**報告されるすべての場所で名前を挙げます。** 除外されたシンボルはすべて、
パス・行・サイズとともに名前が挙がります。プロンプト（`Left out (…): read these
yourself if a hunk needs them.`）、各レビュアーエントリー、`consolidated.json` と
`consolidated.md`、そして `review status` です。プロンプトで名前を挙げるのは先頭の 20 件までで、
残りは件数だけを示します（`- and N more, named in `review status` and consolidated.md`）。
この一覧は予算で賄うブロックの一部なので、長くなると、一覧が指し示すはずのシンボルを
押し出してしまうためです。どのシンボルも予算に収まらないときは、プロンプトとレポートに
`no symbol fits within the budget` と示します。抽出しなかったファイルはプロンプトで
理由ごとに件数を示し、スナップショットを取り直せば解消する 2 つの理由については
名前も挙げます。`consolidated.md` と `review status` では、すべてを理由とともに
名前を挙げて示します。

```json
"surrounding": {
  "shared": true,
  "mode": "enclosing",
  "reason": "",
  "budget": 15000,
  "adopted_chars": 3100,
  "trimmed_chars": 9812,
  "context_chars": 3521,
  "adopted": [
    {"path": "app/models/user.py", "symbol": "User", "kind": "class", "relation": "encloses",
     "start": 12, "end": 88, "chars": 3100, "includes": ["User.save"]}
  ],
  "trimmed": [
    {"path": "app/cli.py", "symbol": "run", "kind": "function", "relation": "encloses",
     "start": 610, "end": 826, "chars": 9812, "reason": "budget"}
  ],
  "skipped": [{"path": "web/app.js", "reason": "not python"}]
}
```

これは `consolidated.json` の最上位のブロックで、`shared: true` になるのは、この
スナップショットのすべてのレビュアーに同じコンテキストが渡された場合だけです。
そうでない場合 — 設定を変えた後の `--only` — は `shared: false` と `by_reviewer`
になり、レビュアーごとに 1 つのレコードを持ちます。設定が off のままプロンプトを
組んだレビュアーは `null` です。プロンプトを組む前に失敗したレビュアーは
レコードを持たず、ここには一切現れません。それが失敗したことは Reviewers 表が
すでに示しています。設定が off のとき、または設計ラウンドでは、このキーは
どこにも書かれません。

**Coverage は変わりません。** Coverage は *diff* がインライン化されたかどうかで
決まります。採用されたコンテキストも除外されたコンテキストも、`coverage.round` と
`coverage.change` のどちらも動かしません。すべてのシンボルを除外したラウンドも
complete のままで、diff がファイルとして渡されたラウンドは partial のままです。
`snapshot.budget_chars` にはこれが含まれます — [Coverage](#coverage) を参照して
ください。

**どのラウンドか。** 修正ラウンドを含むすべてのコードラウンドです。
インクリメンタルラウンドは、そのラウンドのツリーから読んだ、修正の hunk を囲む
シンボルを受け取ります。設計ラウンドには何も付きません。

**囲むシンボルの次に来るもの。** 順序は今の時点で固定しておきます。後から
コンテキストの種類を足しても、すでに採用されているものの順序が変わらないように
するためです。

| 優先順位 | コンテキスト | 状態 |
| --- | --- | --- |
| 1 | 変更箇所の周辺: 囲む関数・メソッド・クラスと、削除に隣接する `adjacent` のシンボル | 実装済み |
| 2 | 変更箇所が呼び出す関数・メソッド | 未実装 — ファイルをまたいだシンボル解決が必要 |
| 3 | 変更箇所が属するクラス・モジュール | 未実装 — 1 のクラス候補が一部をカバーする |
| 4 | 呼び出し元・呼び出し先 | 未実装 — 同上に加えて逆引きの索引が必要 |
| 5 | 関連するテスト | 未実装 — テストを見つけるための規約が必要 |
| 6 | その他 | 未実装 |

候補は `(priority, relation, chars, path, start)` で順位付けされ、優先順位 1 だけの
今は `(relation, chars, path, start)` になります。優先順位 2 と 4 にはファイルを
またいだ索引と解決器が必要で `context.py` が倍になる一方、1 の効果はまだ計測
されていませんでした — そのため、まず 1 を off で出荷しました。1 の効果は、
`review run --surrounding none|enclosing` で 1 つのスナップショットをあり・なしの
両方でレビューし、`optimization report` のペアの数値を読んで測ります
（[周辺コンテキストの効果を測る](limits.md#measuring-what-surrounding-context-does) を
参照してください）。そうして測ったところ、1 でレビューは安くならず、採用した分が
そのまま費用に上乗せされました。そのため、さらに多くを渡す優先順位 2〜6 は進めません。

<a id="design-review"></a>

## 設計レビュー

間違えうるコードがまだ存在しない段階での、同じレビュアー陣によるレビューです。
`review.design.enabled`（デフォルトは `false`）で有効にします。

```bash
dev-orchestra config set review.design.enabled true
dev-orchestra review run --design
dev-orchestra review show --design
dev-orchestra review triage --design F1 --status accepted --note "confirmed"
dev-orchestra review fix-brief --design --output .ai/execution/design-fix-brief.md
```

**入力は diff ではなく plan です。** `review run --design` は `.ai/plan.md` を
`.ai/reviews/design/review-target.md` に凍結し、それが答えている設計リクエスト
（`--request <path>`、デフォルトは `.ai/execution/design-request.md`）と一緒に
ハッシュ化します。plan とリクエストが同じなら同じラウンドであり、plan を書き直せば
次のラウンドになります。git は関与しないので、一度もリポジトリになったことのない
ディレクトリでも設計レビューは動作します。ディスク上に plan がない場合、コマンドは
終了コード 2 で終了し、先に architect を実行するよう伝えます。これにより、「設計
ステージがなければ設計レビューもない」ということが、慣習ではなく仕組みとして成り
立ちます。

**プロンプトは別の問いを投げかけます。**「このコードは正しいか」ではなく、「これに
従えば正しいものができるか」です。plan が挙げるファイルやシンボルは存在するか、
現在の挙動についての記述は正しいか、すべての呼び出し元をカバーしているか、
Test Strategy は十分か、といった点です。各組み込みロールも同じように向け直され、
`security` は diff が何をするかではなく、提案が何を通してしまうかを問います。
そのため `File:` には plan のセクション（`plan.md#Proposed Change`）か、plan が
見誤っているリポジトリのパスを指定し、`Line:` は通常 `n/a` になります。

**成果物は独自のものです。** `reviews/design/` 配下に、レビュアーごとのレポート、
`consolidated.md` / `.json`、凍結された plan、そして全ラウンドの統合レポートを持つ
`rounds/`（[再レビュー](#re-review) を参照）が置かれます。ファイル名のプレフィックス
ではなくディレクトリになっている理由はこれに尽きます。ラウンドカウンターと
トリアージは統合レポートの中にあり、設計ラウンドがコードレビューのカウントを
進めたり、それによって拒否されたりすることがあってはならないからです。
`review show`、`review triage`、`review fix-brief`、`review status` はいずれも
`--design` を受け付け、代わりにそちらのコピーを読みます。このフラグがなければ、
設計の指摘を目にすることはありません。`--base` はここでは意味を持たず、無視されます。

**最適化ゲートとレビュアー陣の縮小は適用されません。** plan について何かを語る
テスト結果はなく、測るべき diff もありません。そして設計上の判断こそ、モデル間の
意見の相違がそのコストに見合う場面なので、毎ラウンド、レビュアー陣全員が実行
されます。`review.max_findings` は引き続き適用され、それが未設定の場合は
`optimization.level` が上限を決めます。設計ラウンドは、`optimization report` が
出力するあらゆる率（有効だったレベル、ゲートの判定、レビュアー陣の縮小、エスカ
レーション）から意図的に除外されています。どのレベルも設計ラウンドについて何も
決めていないからです。その**コスト**は、コードレビューの行の隣に独立した行として
報告され、コードレビューと平均されることはありません。

**指摘の反映**は architect の再実行であり、新しいステージではありません。修正
リクエスト（元のリクエスト、ブリーフ、そして「`.ai/plan.md` を読み、すべての
セクションを残したまま書き直すこと。各指摘について、対処したか、しなかったなら
その理由を述べること」）を書き、それに対して `run architect` を実行します。これは
`budgets.architect` を消費するため、新しい予算キーは存在しません。残るのは直前の
plan だけで、`review-target.md` に凍結されています。書き直しはそれ以外を上書き
します。上限に達したラウンドの指摘も反映されます。plan が凍結されたものと異なる
か、そのラウンドの後に architect が回答するまで、`review status --design` は
`final_revision: pending` と表示し、拒否されるのはその修正版の再レビューだけです。

**コスト。** 1 ラウンドのコストは、コードレビューの 1 ラウンドとほぼ同じです。
レビュアーは plan が挙げるファイルを読みます。`review.design.max_iterations`
（デフォルトは 2）がラウンド数の上限を決め、`1` が安価な設定です。1 ラウンド、
再レビューされない修正 1 回、その後は人に確認します。

<a id="when-a-review-does-not-run-or-runs-smaller"></a>

## レビューが実行されない場合、または縮小して実行される場合

`optimization.level`（デフォルトは `balanced`）は、どのレビュアーも開始する前に、
ラウンドについて 3 つのことを決めます。完全な表は `references/configuration.md`
にあります。ここで重要なのは、それがレビューに対して何ができて何ができないかです。

**ラウンドを完全に拒否できます。** 直近の `state record test ok|failed` が失敗を
記録していた場合です。拒否は、何も実行されていなくても `refused` ラウンドとして
記録されます。スキップされたラウンドはレベルが節約できる最大のものであり、痕跡を
残さない節約は数えられないからです。`optimization report` はこれをカウントします。
自身のテストに通らないツリーをレビューすると、すでに分かっている問題にレビュアーを
費やすことになります。`--force` で上書きできます。テスト結果が記録されていない
ツリーは拒否*されません*。警告を出して実行します。「誰も書き留めなかった」ことは
「失敗した」ことではないからです。

**大きすぎる変更は、そのどれよりも前に拒否されます。**
`review.context.max_chars`（400,000）は、1 ラウンドが送る変更本文（diff、または
plan とそれが答えるリクエスト）の最大量です。これを超えると、`review run` は何も
レビューせずに終了コード 3 で終了します。ラウンドが課金される前、設計パスでは
plan が凍結される前です。収まるように切り詰めることだけは決してしません。変更の
一部だけを渡されたレビュアーには、どの部分が欠けているのか分からないからです。
上限内に収める方法は、`--base`、`review.exclude`、変更の分割、または plan の短縮
です。`--force` は人間のためのものなので、上限を超えた自動ワークフローは
*not reviewed* と報告して停止し、ラウンドが実際に変更をレビューするまで `status`
はそう言い続けます。2 回目の拒否はそれに当たらず、帳簿上の操作も当たりません。
この拒否はゲートによる拒否と同じように記録され、両者を区別するために
`refused_by: "context"` が付きます。強制実行されたラウンドは、すべての
レビュアーエントリと `consolidated.json` の `snapshot` ブロックに `over_budget` を
持ちます。この数値と、強制実行が何を保証し何を保証しないかについては
`references/limits.md` を参照してください。

**レビュアー陣を 1 人に減らせます。** `aggressive` のときで、変更が
`low_risk_max_files` と `low_risk_max_lines` を下回り、高リスクのパスに触れていない
場合です。縮小されたレビュアー陣では、スペシャリストよりも `general` レビュアーが
優先して残されます。単独のセキュリティレビュアーは正しさのバグを報告しません。
それを探さないように指示されているからです。`--only` で上書きでき、縮小はそれを
決めた数値とともに出力されます。

**高リスクの変更を安くすることはできません。** `optimization.high_risk_paths` に
マッチするもの（認証、シークレット、決済、マイグレーション、SQL、暗号、デプロイ
設定）は、レベルの設定にかかわらず `quality` にエスカレーションされます。レビュアー
陣は全員、指摘の予算も満額、ゲートなしです。パターンは自由に置き換えられますが、
エスカレーションを無効にすることはできません。

決してしないのは、指摘を落とすこと、レビュアーのレポートを統合してしまうこと、
自分が動作したことを隠すことです。すべての判断は出力され、実行状態に記録され、
`review run --json` と `status --json` の `optimization` の下で返されます。

<a id="roles"></a>

## ロール

組み込みロールには、プロンプトの中でより的を絞ったガイダンスが与えられます。

| ロール | 重点 |
| --- | --- |
| `general` | 正しさ、リグレッション、エッジケース、セキュリティ、パフォーマンス、データ整合性、並行性、エラー処理、テストの抜け、不要な複雑さ |
| `security` | 認証/認可、インジェクション、デシリアライゼーション、SSRF、パストラバーサル、シークレットの扱い、安全でないデフォルト、アクセス制御のリグレッション |
| `performance` | 計算量、N+1 クエリ、インデックスの欠如、不要な I/O、際限のないメモリ使用、ブロッキング呼び出し、キャッシュの無効化 |
| `test` | 変更された挙動のカバレッジ、意味のないアサーション、不安定になりやすいパターン、テストされていないエラーパス |
| `architecture` | レイヤリング、責務、抽象化の漏れ、結合度、契約の形、既存の慣習との整合性 |
| `database` | マイグレーションの安全性、ロック、バックフィル、可逆性、制約、インデックスのカバー範囲、トランザクション境界 |
| `frontend` | 状態の扱い、描画コスト、アクセシビリティ、レスポンシブレイアウト、エラー/ローディング状態、クライアント側のみのバリデーション |
| `backend` | API 契約、バリデーション、ステータスコード、冪等性、トランザクション、ジョブのセマンティクス、可観測性 |

それ以外の文字列も有効なカスタムロールで、汎用的なスペシャリストとしての枠組みが
与えられます（`role: accessibility` → 「アクセシビリティのスペシャリストとして
レビューする」）。レビュアー陣を再現可能にするため、カスタムロールはプロジェクト
設定に書いておく価値があります。

`general` では、スタイルだけに関する所見の重大度は最大でも low です。命名に関する
細かい指摘を 4 つ返して null ポインターのパスを見逃すレビューは、失敗したレビュー
です。

レビュアーを追加したら、数ラウンドたったところで `optimization report` の採点表で
その行を確認してください。外すべきレビュアーを知らせる仕組みは無く、何も加えない
レビュアーは `reviewer remove` でパネルから外せます。

<a id="output-schema"></a>

## 出力スキーマ

レビュアーには、次のとおりの形式が求められます。

```markdown
## Finding
- Severity: critical | high | medium | low
- File: <path relative to the repo root>
- Line: <number, range, or n/a>
- Category: <correctness | security | performance | tests | …>
- Problem: <what is wrong, 1-2 sentences>
- Impact: <what breaks, and when>
- Evidence: <the code or hunk that shows it>
- Fix: <the concrete change>
```

問題のないレビューは、正確に `NO_FINDINGS` を返します。

<a id="output-limits"></a>

### 出力の上限

プロンプトは返ってくる内容に上限を設けます。

| 上限 | デフォルト | 設定箇所 |
|---|---|---|
| レビュアーあたりの指摘数 | 6 | `review.max_findings`（0 = 上限なし） |
| 指摘あたりの Evidence の行数 | 3 | `review.py` の `MAX_EVIDENCE_LINES` |
| 指摘あたりの Fix の行数 | 2 | `review.py` の `MAX_FIX_LINES` |
| 前置き、まとめ、結びの言葉 | なし | プロンプトで固定 |

高くつくのは出力の方向です。トークンあたりのコストは入力の数倍であり、しかも
レビュアーの出力は、統合されるときにもう一度、修正担当のブリーフとしてさらに
もう一度課金されます。上限のないプロンプトは、low の指摘 20 個と、それぞれに
画面いっぱいの引用コンテキストを招きます。

上限がかかるのは量であって、判断ではありません。上限を超えたレビュアーには、
黙るよう求めるのではなく、最も深刻な指摘を挙げるよう求めます。そして**実際に
返ってきたものは何も落とされません**。すべての指摘がパースされて保持され、上限を
超えたレビュアーは stderr に報告されます。どの指摘を捨てるかを決めるのは
トリアージであり、トリアージはプロンプトではなくオーケストレーターの仕事です。

認識できる形式の指摘も `NO_FINDINGS` も返さなかったレビュアーは、ステータス
`unparsed` として記録され、**failed** として数えられます。読めないレポートは
コードに問題がないことの証拠ではなく、それをそう扱うことは、レビューツールに
とって最悪の失敗の仕方です。

<a id="coverage"></a>

## Coverage

**`review.context.inline_chars`**（デフォルトは 400,000 文字）を超える変更本文は、
プロンプトに入りません。代わりにレビュアーには凍結されたスナップショットのパスが
渡され、それを読むよう求められます。そして実際にどれだけ読まれるかは、こちらからは
知りようがありません。Claude Code の `Read` はデフォルトで 2,000 行で止まるので、
レビュアーは変更の 5 分の 1 しか見ずに `NO_FINDINGS` と答えることがあり、その
答えには、本当に問題のないレビューと区別できる要素が何もありません。

そのため、判定は答えから取りません。変更本文をファイルとして渡されたレビュアーは、
何を返したかにかかわらず、ステータス **`partial`** として記録されます。その指摘は
保持され、他の指摘と同様にトリアージされます。欠けているのは、変更全体を見たという
保証です。`partial` は `failed` とは別に数えられ（`reviewers_ok`、
`reviewers_partial`、`reviewers_failed` の合計が `reviewers_total` になります）、
`unparsed` はそれより優先されます。誰にも読めないレポートのほうが、より具体的な
事実だからです。

デフォルトは `review.context.max_chars` と同じ数値なので、境界は 2 つではなく
1 つになります。それ以下ならラウンドは実行されて完全であり、それを超えると
ラウンドは拒否され、それを超えて強制実行されたラウンドは `partial` です。
`inline_chars` を `max_chars` より小さく設定すると、その間に、ラウンドが実行されて
`partial` として記録される帯が生まれます。それがこの設定の目的であり、そのコスト
でもあります。上限は設定値なので、すべてのラウンドは測定の基準にした数値を記録
します。`consolidated.json` の `coverage.inline_chars` と、各レビュアーエントリの
`inline_chars` です。

この 4 つは、レビュアー表全体を数えたものです。レビュアー表は意図的にラウンドより
長く残ります（後述）。`counts` は同じ 4 つを `snapshot_reviewers_total`、
`snapshot_reviewers_ok`、`snapshot_reviewers_partial`、`snapshot_reviewers_failed`
としてもう一度持ち、こちらはレポートが対象とするスナップショットが刻印された
エントリについて数えたものです。これは、すべての `coverage` の値が導出される集合
です。どちらも、一方が他方と取り違えられないように名前が付けられています。
`no reviewer has run against this snapshot` の横に `0 ok / 0 total` とあれば 1 つの
答えですが、その横に `2 ok / 2 total` とあれば、1 つの文書に 2 つのスナップショットが
混在しているということです。`consolidated.md` は表の集計を出力し、両者が異なる
場合は 2 行目にスナップショットの集計を出力します。`review status` はスナップ
ショットの集計を報告します（トップレベルの `reviewers_partial` はそちらであり、
`counts` は両方を持ちます）。

レビュアーに、このいずれかを申告させることはありません。申告は、それがされ*なかった*
場合について検証できません。また、プロンプトの最後は
"Findings or `NO_FINDINGS` only" で終わり、これはそれ以前に求めたことをすべて上書き
します。プロンプトはラウンドが何として記録されるかを伝えますが、記録はこちら側で
行います。

`consolidated.json` は、ラウンドの答えをトップレベルに持ちます。

```json
{
  "coverage": {
    "round": "complete",
    "change": "unverified",
    "unverified_since": 1,
    "change_chars": 130412
  }
}
```

以下の値はすべて、レポートが対象とするスナップショットが刻印されたレビュアー
エントリから導出されます。各エントリは `snapshot` を持ちます。これはレビュアーの
レポートに刻印されるのと同じ短い sha です。レビュアー表は意図的にラウンドより長く
残るため、これが必要になります。`--only` は新しい実行を表にマージし、今回実行され
なかったレビュアーも表が完全であるように残されます。以前のスナップショットの
エントリがこのラウンドの coverage ではないのは、以前のスナップショットのレポートが
このラウンドの指摘ではないのと同じです。`snapshot` は新しいキーです。これを知らない
読み手には、これまでどおりのエントリが見えます。

**`coverage.round`**：**このラウンドの変更本文**（`review-target.diff`、設計
ラウンドでは `review-target.md`。インクリメンタルラウンドでは、その diff は修正
だけです）が、このラウンドですべてのレビュアーのプロンプトに丸ごとインライン化
されたかどうか。

- `complete`：すべてのレビュアーにインライン化された。**変更全体については何も
  語りません。** インクリメンタルラウンドでは「修正が完全に示された」ことを意味
  します。
- `unverified`：1 人以上のレビュアーにファイルとして渡された。
- `none`：このスナップショットに対して実行されたレビュアーがいない（1 人も設定
  されていない、取得後に 1 人も実行されていない、またはすべてのエントリがこの
  バージョンより前のもの）。

**`coverage.change`**：**レビュー対象の変更全体**。

- `unverified`：このワークフローとブランチに、`round` が `unverified` だった
  ラウンドがあり、それ以降、インクリメンタルでないスナップショット（空の
  `incremental_from`）が `round: complete` で、かつ*そのスナップショットの*
  レビュアーが少なくとも 1 人 `ok` という状態でレビューされていない。
- `complete`：それが起きた、または unverified になったラウンドが一度もない。
- `none`：このワークフローとブランチでは、まだ何もレビューされていない。

**`coverage.unverified_since`**：`change: unverified` が始まったラウンド番号。その
番号が現在のカウントに属する場合に限ります。それ以外は `null` です。これには、
系統（lineage）の変化をまたいでマークが引き継がれた `unverified` の変更も含まれます。
ラウンドカウンターはそこでリセットされる（[Re-review](#re-review) を参照）ため、
その番号はカウントに存在しないラウンドを指すことになり、「since round 3」の横に
`iteration 1/2` が表示されてしまいます。引き継ぎの目的はマークであり、マークは
残ります。番号はそうではなく、それが属していたカウントとともに破棄されます。
マークは `coverage.change` から読み取り、決してこの値が設定されているかどうかから
判断しないでください。

**`coverage.change_chars`**：このラウンドの変更本文が何文字だったか。実行時の記録に
よるものです（どの実行も記録しなかった場合は `null`）。

**`coverage.inline_chars`**：そのサイズの測定基準になった
`review.context.inline_chars`。どちらの数値も、ラウンドのマークを決めたエントリ
（ファイルを渡されたレビュアーがいれば、その最初の 1 人）から読み取られます。
そのため、この組は 1 つのラウンドの 2 つの数値であり、あるラウンドのサイズと別の
ラウンドの上限の組になることはありません。`--only` の後では、同じスナップショットの
エントリが 2 つの設定の上限を持っていることがあるからです。`change_chars` が
`null` のときと、上限が設定可能になる前に記録されたラウンドでは `null` です。当時の
上限は 120,000 でしたが、誰も書き留めておらず、ここでそれを捏造することはしません。
上限が設定値であるために記録しています。`partial` のラウンドとサイズだけでは、
変更が大きかったのか上限が低かったのかが分からないからです。

**`snapshot.over_budget`**：`sha256` と `files` の隣にあり、このラウンドが
`--force` によって `review.context.max_chars` を超えて送られたかどうかを表します。
同じ理由で同じエントリから導出されます（上限とフラグは凍結されたファイルではなく
実行に属するからです）。強制実行されなかったラウンドと、上限が存在する前に書かれた
すべてのレポートでは `false` であり、それはそのすべてにとって正しい答えです。

**`snapshot.budget_chars`**：その上限が測ったサイズで、`consolidated.md` の
`Change:` 行が出力する値です。`coverage.change_chars` ではありません。設計
ラウンドでは、予算は plan *と*リクエストを数えますが、レビュアーに渡される本文は
plan だけだからです。[周辺コンテキスト](#surrounding-context)を採用したコード
ラウンドでは、diff に採用したコンテキストを足したものになります。どちらも
プロンプトに入ったからです。どの実行も記録しなかった場合は `null` です。`over_budget` と
同様に、このブロックだけでなくすべてのレビュアーエントリにも記録され、このブロックは
それらのエントリから導出されます。

この 2 つが分かれているのは、インクリメンタルラウンドが修正だけをインライン化する
からです。*このラウンド*がインライン化したもので変更全体を判定すると、修正だけの
ラウンドが partial なラウンドを洗浄できてしまいます。指摘を受け入れ、修正し、修正を
インライン化し、`NO_FINDINGS`、問題なし。変更の 5 分の 4 は誰にも読まれないまま
です。そのため、マークはラウンドをまたいで引き継がれます。

引き継ぎは**ワークフローとブランチ**単位で行われます。ラウンドカウンターのキー
からベースを除いたものです。ベースは「どの変更か」を言い表すもう 1 つの方法であり、
まさにそれゆえにマークをベースに結び付けることはできません。`--base` で絞り込むと
ラウンドは小さくなりますが、変更が読まれた度合いは変わりません。ベースをキーに
したマークは、マークを見た人が最初に試すことで消えてしまうでしょう。その代償、
それも払う価値のある代償は、同じブランチ上の 2 つ目の無関係な変更が、フルスナップ
ショットがインラインでレビューされるまでマークを引き継ぐことです。

これで得られるのは、マークがベースの変更を*生き延びる*ことであり、あらゆる絞り
込みに対する保証ではありません。`coverage.change` が言っているのは、スナップショット
が定義する変更全体を、レビュアーが完全に見たということです。より近いコミットに
ベースを移し、小さくなった変更を完全にレビューすれば、その小さな変更について
`complete` と報告されます。そのため、案内される対処法は、変更を分割してそれぞれの
部分を完全にレビューすることであり、ベースを動かして終わりにすることではありません。

マークを解除するのは変更そのものへの変更であり、別のラウンドでも、同じ変更をより
狭く見ることでもありません。同じスナップショットを再実行すれば、同じプロンプトが
送られ、同じ判定が返ります。

| 状態 | 解除する方法 |
| --- | --- |
| `round: unverified` | 変更を分割してそれぞれの部分をレビューし、各本文がインラインに収まるようにする。または、大きなプロンプトに支払う価値があるなら、`review.context.inline_chars` を引き上げてスナップショットを取り直す |
| `change: unverified`、`round: none` | `review run`。このスナップショットに対して実行されたレビュアーがおらず、まだ何も読まれていない |
| `change: unverified`、このラウンドは complete、`ok` のレビュアーなし | `ok` で戻らなかったレビュアーを再実行する。このスナップショットはインライン化されたが、誰にも読まれていない |
| `change: unverified`、このラウンドは complete、`ok` のレビュアーあり | 変更全体がインラインに収まるようになったら `review snapshot --full`、その後 `review run`。このラウンドは修正だけをインライン化した |
| 設計ラウンドでのいずれか | `.ai/plan.md` をインラインに収まるまで短くして（または `review.context.inline_chars` を引き上げて）、設計ラウンドを再実行する。`review snapshot` はコードのスナップショットを書き出すもので、`--design` 形式はない |

1 行目には例外が 1 つあり、その場合は `review status` が代わりにそう伝えます。
`review.context.inline_chars` が、ラウンドが記録したサイズを超えるまで引き上げられた
後は、同じスナップショットが今ならインライン化される*はず*なので、上限が変わった
ことと、それに対してもう一度 `review run` を実行することを伝えます。そうしなければ、
すでに収まっている変更を分割することや、すでに引き上げた上限を引き上げることを、
通常のアドバイスが読み手に勧めてしまうからです。

中央の 3 行は、1 つのマークについて、欠けているものがそれぞれ異なる 3 つのケース
です。間違ったものを挙げると、読み手はたった今やったことをやり直すことになります。
そのため状態は一度だけ分類され（`coverage_state`）、`consolidated.md` と
`review status` はその 1 つの答えを言葉にします。レポートはラウンドが何であるかを
述べ、ステータス行はそれに対して何をすべきかを述べ、同じレポートを異なるように
説明することは決してありません。

`review run` は、`ok` で戻ったレビュアーが 1 人もいないラウンドでは、partial を
含めて、終了コード **1** で終了します。そのラウンドは、変更に問題がないという主張を
何も生み出さなかったのであり、それはすべてのレビュアーが失敗したのと同じことです。
`review status` は両方の値と、それらを変えうる 1 つのアクションを出力します。

このバージョンより前に記録されたラウンドは、レビュアーエントリに `delivery` も
`snapshot` も持たず、何かを仮定するのではなく導出から除外されます。このバージョン
より前のレポートには `coverage` ブロックがまったくなく、`consolidated.md` も
`review status` もそれを `none` とは説明しません。測定されていないラウンドは、
測定されて空だったラウンドではないからです。これまでに記録されたすべての実行は
上限を十分に下回っていました（最大で 99,814 文字）。したがって、既存の履歴の中に、
実際にはそうでないのに問題なしと読まれているものはありません。記録が単に何も
語っていないだけです。

設計レビューのリクエストセクションは、*coverage* のルールの既知の例外です。設計
ラウンドがレビューする変更本文は plan なので、リクエストはサイズにかかわらず
インライン化されます。ただし、後述のサイズによる拒否の例外ではありません。こちらは
plan とリクエストの合計で測られます。どちらもプロンプトに入るからです。

パーサーは意図的に寛容です。`**Severity:** high`、`**Severity**: high`、
`- Severity: high` を受け付け、`Finding` の見出しレベルは問わず、
`Recommended fix`/`Recommendation` を `Fix` の同義語として扱い、複数行の値を受け
付け、パスを正規化します（`./a\b.py` → `a/b.py`）。不明な重大度は `medium` に
なり、`nit`、`minor`、`style`、`info` は `low` に、`blocker` は `critical` に
なります。problem も evidence もないブロックは破棄されます。

<a id="deduplication"></a>

## 重複排除

2 つの指摘は、**同じ箇所**（同じファイルで、行番号の差が 10 以内、または行番号が
ない）にあり、problem と推奨修正のテキストが類似度 0.72 以上で一致する場合に
マージされます。

マージでは、**最も高い**重大度と、各テキストフィールドの**最も長い**版が残され、
それを報告したすべてのレビュアーが記録されます。

```json
{
  "id": "F1",
  "severity": "critical",
  "file": "app/models/user.rb",
  "line": "42",
  "category": "correctness",
  "reported_by": ["claude-general", "codex-security"],
  "duplicate_count": 2,
  "triage": "needs-triage",
  "triage_note": ""
}
```

指摘は重大度順に `F1…Fn` と番号が振られるので、`F1` は常に最も深刻なものです。
独立した 2 人のレビュアーの意見が一致すれば、その指摘が本物である事前確率は
上がりますが、それで真になるわけではありません。

<a id="why-auto-merge-stays-conservative"></a>

### 自動マージが保守的なままである理由

自動マージが捕捉するのは、ほぼ同一の言い換えだけです。**モデルをまたいだ重複は、
文章としてはほとんど似ていません。** そして数値は近くすらありません。同じ diff に
対する 2 つのプロバイダーの実際の出力で計測したところ、重複と確認されたペアの
テキスト類似度は **0.03** だったのに対し、無関係なペアは **0.29** でした。前者を
マージするしきい値は、後者も大量にマージしてしまいます。そして 2 つの異なるバグを
1 つにまとめると片方が隠れてしまい、それは 1 つの問題を 2 回挙げることより悪い
失敗です。

そこで、緩いシグナルは切り分けられています。**異なる**レビュアーからの、同じ
ファイルで同じコードを引用している指摘は、**重複の可能性がある**ものとして報告
されます。

```markdown
## Possible duplicates (confirm during triage)

- F1 ~ F7  (`cart.py`, shared: `code.split`)
- F3 ~ F8  (`cart.py`, shared: `i.price`)
```

ペアは、共有されているトークンの珍しさで順位付けされます。その 2 つの指摘だけが
言及しているコードは、すべての指摘が引用する式よりもはるかに強い証拠です。*同じ*
レビュアーからの指摘がペアにされることはありません。レビュアーは同じ問題を 2 回
報告しないよう指示されているので、同じレビュアーの 2 つの指摘は、構造上 2 つの
問題だからです。

各ペアは、トリアージの際に確認するか却下します。

```bash
dev-orchestra review triage F7 --status duplicate --note "same as F1"
```

上のサンプルでは、これで本物の重複をすべて（3 件中 3 件）捕捉し、その代償は重複
ではなかった 3 件の提案でした。このトレードオフは意図的なものです。見逃した重複の
コストは修正担当の余分な作業ですが、誤ったマージのコストはバグ 1 つです。

<a id="triage"></a>

## トリアージ

```bash
dev-orchestra review show                       # the consolidated report
dev-orchestra review triage F1 F4 --status accepted --note "confirmed"
dev-orchestra review triage F2 --status rejected --note "guarded by caller"
dev-orchestra review triage F3 --status needs-investigation
dev-orchestra review show --accepted            # what the fixer will see
```

| ステータス | 意味 |
| --- | --- |
| `needs-triage` | デフォルト。まだ判定されていない。 |
| `accepted` | コードに照らして検証済み。修正担当が対処する。 |
| `rejected` | 誤検知、またはスコープ外。理由を記録する。 |
| `duplicate` | 重複排除で見逃された、別の指摘と同じもの。 |
| `needs-investigation` | まだ判断できない。調査してから再度トリアージする。 |

トリアージの判断は、内容（ファイル + 正規化された problem のテキスト）をキーに
しています。`F1..Fn` の番号は位置に基づくもので、毎ラウンド振り直されるため、
キーにはしていません。そのため、より深刻な指摘が修正されてその下のすべてが番号を
振り直されても、判断はその指摘についていきます。指摘の文言が変われば判断は失われ
ますが、それが誠実な結果です。もはや同じ主張ではないからです。

判断のたびに、指摘には `triage_set_at`（UTC、`generated_at` と同じ書式）も刻まれ、
その印は判断とともに次のラウンドへ運ばれます。`review triage --status needs-triage`
と、誰も一度も判定していない指摘とを見分けるのはこの印だけです。再構築された
レポートは既定値として `needs-triage` を書き、印は付けません。この違いは
`optimization report` にとって意味があります。その採点表は、指摘に対する最後の
明示的な判断をラウンドをまたいで有効にするので、採用した指摘を `needs-triage` に
戻せばそこで採用が取り消され、既定値では取り消されません。0.11.0 より前に書かれた
レポートには印がありません。`needs-investigation` は既定値として書かれることが無い
ので判断として読み、`needs-triage` は既定値として読みます。

レビュアーのレポートには、書かれた時点のスナップショットが刻印されます。以前の
スナップショットのレポートは、現在のラウンドに取り込まれずにスキップされます。
そうしなければ、統合し直すたびに、すでに修正された問題を修正担当に渡してしまう
からです。

指摘を受け入れる前に、引用されたコードを*現在の*状態で読み、その主張が（一般論では
なく）このコードベースで正しいかを確認し、推奨された修正が、レビュアーには見え
なかった何かを壊さないかを確認してください。却下する前には、口調ではなく主張その
ものを却下しているのかを確かめてください。

<a id="re-review"></a>

## 再レビュー

ラウンドカウンターは、プロジェクトではなく*この*レビューに属します。カウンターは
統合レポートの中にあり、統合レポートは個々の変更より長く残るため、ワークフロー、
ブランチ、ベースをキーにしています。別のブランチ、別の `--base`、または
`budget reset` でカウントは最初からになります。このキーがなかった頃は、ディレクトリ
で取得されたすべてのスナップショットを数えていたため、無関係な変更を持つ 2 つ目の
ブランチがラウンド 3 から始まって拒否されていました。しかも、それを解除する
サポートされた方法はありませんでした。`budget reset` は台帳をリセットしますが、
カウンターはその中になかったからです。

以前に作業したブランチに戻ることも、新しいレビューです。ブランチごとのカウントは
保持されません。問われるのは、このラウンドが前回のラウンドの続きかどうかだけです。
失敗するなら、拒否する方向ではなくレビューする方向に倒すべきです。

変わっていないのは、予算が止めるために存在するループです。1 つのブランチ上の
1 つの変更に対する、レビュー、修正、再レビューは、依然として上限に達します。

```bash
dev-orchestra review status --json
```

`iteration` は `review run` がスナップショットから導出するので、カウンターの
インクリメントを忘れることで予算を回避することはできません。

`re_review_recommended` は、`review.re_review_severities`（デフォルトは critical +
high）の未解決の指摘が残っており、**かつ** `iteration < max_review_iterations`
（デフォルトは 2）のときに true になります。rejected と duplicate の指摘が妨げに
なることはありません。

再レビューのラウンドは、`review snapshot`（コードが変わったので、スナップショットも
変わる必要があります）→ `review run --iteration 2` → トリアージ → 修正、です。
予算を使い切った場合も、最後のラウンドには修正と再テストが行われます。
`review fix-brief`、`run
review_fixer`、再度のテスト、そして `state record test ok|failed` による記録です
（`final_fix` は `pending` → `retest` → `done` と進みます）。その後、残ったものを
報告して停止し、再レビューはしません。このパイプラインが捕捉するもののうち圧倒的
大部分は 2 ラウンドで捕捉され、3 ラウンド目はおおむね同じ議論の蒸し返しになります。

**すべてのラウンドのレポートが残ります。** `consolidated.json` は現在のラウンドで、
次のラウンドがこれを置き換えます。これを書くたびに
`reviews/rounds/<sha12>-<round_id>.json` にもコピーが書かれ、スナップショットの sha と、
すべてのスナップショットに与えられる `round_id` で名付けられます -- code の
スナップショットは `reviews/review-target.json`、design のラウンドは
`reviews/design/review-target.json` にあります。sha だけでは足りません。同じツリーや
plan を凍結し直すと sha は繰り返し、2 つ目のラウンドが 1 つ目を上書きしてしまうから
です。同じラウンドへの後の書き込み -- `--only` の再実行、`review consolidate`、
`review triage` -- は、live のレポートと同じようにそのコピーを上書きします。現在の凍結の
後に前のラウンドの id のまま作られたレポート -- どのレビュアーもレビューを返さなかった
design ラウンドや、ラウンドのレビュアーが戻る前の `review consolidate` -- にはコピーを
作りません。同じツリーや plan を凍結し直した場合、その id は前のラウンドのキーだからです。成功した
レビュアーを `--only` で再実行すると、両方でそのレビュアーの前のレポートが置き換わる
ので、前の run だけが見つけたものはそのラウンドから消えます。失敗したレビュアーの
再実行では何も失われません。
[`--surrounding` の対](limits.md#measuring-what-surrounding-context-does) の 2 回の
run は 1 回の凍結を読む 1 つのラウンドです。2 回目の run のコピーが 1 回目のものを
置き換え、採点表ではその対は両方の run のコストと、2 回目の指摘とトリアージを数えます
-- 対はトリアージの前に取るので、トリアージが届くのは 2 回目の側です。
`optimization report` はこれらのコピーをレビュアー採点表のために読みます。0.11.0
より前のワークフローには live のレポートしか無く、それ以前のラウンドはすべて、
読めるレポートの無いラウンドとして報告されます。

<a id="the-second-round-only-diffs-the-fix"></a>

### 2 ラウンド目は修正だけを diff する

変更がブランチの場合も同様です。`--base main` は*最初の*ラウンドが何をカバーするかを
示すものです。後のラウンドを修正に絞り込むかどうかは別の問題であり、以前はこの 2 つ
が混同されていました。そのため、ブランチをレビューする通常の方法で、毎ラウンド
ブランチ全体が再送されていました。実際の 3 ラウンドのレビュー 1 件で計測したところ、
diff は 1,867 行から 3,228 行に増え、指摘は 11 件から 5 件に減り、指摘あたりの
コストは $0.20 から $1.00 になりました。

ラウンドの間にベースを変更すると、変更全体が再び対象になります。ベースが違えば
レビュー対象の定義が違うのであり、前の定義に対する修正に絞り込めば、今回誰も
尋ねていない問いに答えることになります。

すべてを `HEAD` に対して diff し直すと、1 行の修正を見るために、ラウンド 2 が
ラウンド 1 と同じコストを（レビュアーごとに）費やすことになりました。そこで
スナップショットは作業ツリーを git の tree オブジェクトとして記録し、次のラウンドは、
前のラウンドが実際にレビューしたツリーに対して diff を取ります。

```
$ dev-orchestra review snapshot
  strategy: git diff <previous round> <now>
  scope:    what changed since the last reviewed round, not the whole change
            whole change kept at .ai/reviews/review-target-full.diff
            reviewers also get the findings the fix was meant to address
```

ツリーは使い捨てのインデックスを通して書き込まれます（`git stash
create` と同じ手法です）。そのため、ユーザー自身のインデックスには一切触れません。
また、新しいモジュールはたいてい変更の中で最も重要な部分なので、未追跡ファイルも
含まれます。

**前提も一緒に渡されます。** レビュアーはステートレスで、他のレビュアーの出力を
見ないので、修正の diff だけでは目的の示されていない変更になります。何を正そうと
していたのかを知らずに「これは正しいか」には答えられません。そのため、インクリ
メンタルラウンドには次のものも含まれます。

- 修正が対処しようとした accepted の指摘（それぞれ 1 行）
- 凍結された変更全体である `review-target-full.diff` へのポインター
- 各指摘が実際に修正されたかを述べ、修正によって新たに生じた問題を報告し、
  列挙された項目が本物だと*仮定しない*よう求める指示

誰が何を報告したかは、意図的に省かれています。指摘は、まだ有効な別のレビュアーの
意見としてではなく、修正担当が作業の元にしたブリーフ（変更についての事実）として
届くので、レビュアー同士が互いの出力を見ることは引き続きありません。計測したところ、
前提のコストは約 80 トークンで、数千トークン分の diff の再送を置き換えます。

`review.context.surrounding: enclosing` のときは、修正ラウンドも、このラウンドの
ツリーから読んだ、修正の hunk を囲むシンボルを運びます —
[周辺コンテキスト](#surrounding-context) を参照してください。

スコープが絞り込まれるのは、インクリメンタルにする対象のラウンドがある場合だけです。

| 状況 | スコープ |
| --- | --- |
| 最初のラウンド | 変更全体 |
| 前のラウンドがレビューされ、accepted の指摘を生み、その後ツリーが変わった | 修正 |
| 前のラウンドで何も見つからなかった、またはすべて rejected だった | 変更全体 |
| 前のスナップショットが一度もレビューされなかった（レビュアーが失敗したので、スナップショットを取り直す） | 変更全体 |
| レビューされたラウンド以降、何も変わっていない | 変更全体 |
| `--base` を指定した | そのベースからの変更全体 |
| `--full`、または `review.incremental_rounds: false` | 変更全体 |

2 行目より後の行はすべて、絞り込むと節約できる以上のコストがかかるケースです。
「一度もレビューされなかった」と「何も変わっていない」の行がなければ、通常の
スナップショットの取り直しが、いつの間にか空の diff になってしまいます。そして、
修正すべきものを何も生まなかったレビューに続くラウンドは、修正の確認ではなく
*新しい作業*のレビューです。レビュアーに渡すブリーフがないので、判断の拠り所の
ない断片ではなく、変更全体が渡されます。

**スナップショットを取り直す前にトリアージしてください。** スコープは accepted の
指摘が存在することを条件に絞り込まれるので、先にスナップショットを取り直すと、
再び変更全体が対象になります。

**絞り込まれたラウンドが問題なしと言えるのは、修正についてだけです。** ラウンド 2
の `coverage.round: complete` は修正が完全にインライン化されたことを示すだけで、
ラウンド 1 でファイルとして渡された変更については何も語りません。そのため
`coverage.change` は別に引き継がれ、ラウンド 2 が `NO_FINDINGS` と答えてもそれは
解除されません。`review snapshot --full` は変更全体を再送します。それがインラインに
収まり、*その*スナップショットのレビュアーが 1 人でも `ok` で戻れば、
`coverage.change` は `complete` に戻ります。[Coverage](#coverage) を参照して
ください。

ツリーが記録されるのは、ラウンドがそれを使う可能性がある場合だけです。`--base` と
`review.incremental_rounds: false` はどちらも使わないことを示します。そして記録する
ということは、未追跡かつ無視されていないすべてのファイルをハッシュ化してオブジェクト
データベースに入れることを意味し、誰も ignore し忘れた大きなディレクトリがある
リポジトリでは、安くもなければ目立たなくもありません。そのようなスナップショットの
次のラウンドはツリーを見つけられず、変更全体を対象にします。これはフォールバック
先として安全な方向です。`review.context.surrounding: enclosing` は、囲むシンボルを
抽出するために、それでも diff の前にツリーを書き出します。これは `tree` ではなく
`surrounding.tree` として保持されるので、次のラウンドをインクリメンタルにする
ことはありません。

<a id="running-reviews-on-their-own"></a>

## レビューを単独で実行する

レビューパイプラインは、ワークフローの他の部分がなくても役に立ちます。

```bash
dev-orchestra review snapshot --base main
dev-orchestra review run
dev-orchestra review show
```

便利なフラグ: 一部だけを実行する `--only <id-or-role>`、デバッグ中に 1 つずつ実行
する `--sequential`、すべてのレビュアーに同じ追加の背景情報を与える
`--context "…"`、実行ごとの制限時間を上書きする `--timeout`。
